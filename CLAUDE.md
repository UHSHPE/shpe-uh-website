## Project Overview
SHPE University of Houston chapter website. React + Vite frontend, FastAPI + PostgreSQL backend.

## Stack
- **Frontend:** React 19, Vite, Tailwind CSS v4, Framer Motion, React Router v7, Axios, qrcode.react (QR rendering for chair-side event check-in)
- **Backend:** FastAPI, SQLModel (ORM), PostgreSQL 17 (via Docker, `postgresql+psycopg://` — psycopg 3 driver), PyJWT, pwdlib (Argon2 hashing), slowapi (rate limiting)
- **Auth:** JWT bearer tokens via `/login`; `/signup` creates an **unverified** account and emails a verification link (no token returned) — the account can't log in until `/verify-email` confirms it. Self-service password reset via `/password-reset/*`

## Running Locally
**Database** (requires Docker):
```bash
docker compose up -d
```
Starts PostgreSQL 17 on `localhost:5433` (see `docker-compose.yml`). Must be running before the backend or its tests will connect.

**Backend** (requires `.venv` activated):
```bash
cd backend
alembic upgrade head  # only needed after a schema change or a fresh/wiped db
python main.py        # or: uvicorn main:app --reload
```
Runs on http://localhost:8000

`create_db()` no longer creates tables (Alembic owns the schema), so on a fresh or wiped database the app boots fine and then 500s on the first query until `alembic upgrade head` has run. Once applied it's a no-op, so it's harmless to run every time.

**Frontend:**
```bash
cd frontend
npm run dev
```
Runs on http://localhost:5173

## Deployment (Vercel Pro + Railway + Squarespace DNS)
Target: frontend on **Vercel Pro** (paid tier — the free Hobby tier bans commercial use and the shop sells merch), backend on **Railway** (~$5/mo, persistent volume mounted at `/data`), DNS at **Squarespace**, nightly backups to S3-compatible object storage. `specs/FUTURE_DEPLOYMENT.md` (gitignored) holds the full runbook.

- **`config.is_production()` is the single answer to "am I in production?"**, and `square_is_production()` the same for `SQUARE_ENVIRONMENT`. Both strip and lowercase; both read env at **call** time (never cached in a module constant — `docs_urls()` runs at import, and the test suite monkeypatches `ENVIRONMENT`). Every call site imports the function; see the "What NOT to do" entry for the bug that made this necessary.
- **`config.py` is the single knob for every writable path.** `DATA_DIR` derives `RESUME_DIR` and `PRODUCT_IMAGE_DIR`. Unset it reproduces the old `backend/`-relative layout, so local dev is unchanged. The **database is not here** — it lives in Postgres via `DATABASE_URL` — but uploads are still on disk, so a deployment without a mounted volume loses every resume and product image on the next deploy. `config.py` deliberately does **no `mkdir` at import** — creation happens in `create_db()`, so importing it never touches the filesystem (tests monkeypatch these paths).
- **The route modules re-export their upload dir as a module attribute** (`RESUME_DIR = config.RESUME_DIR`), NOT `config.RESUME_DIR` at the call site. Five tests monkeypatch `routes.<module>.RESUME_DIR`/`PRODUCT_IMAGE_DIR` to a `tmp_path`; reading through the config module would bypass the patch and silently break all of them.
- **The database is Postgres** (`DATABASE_URL`, `pool_pre_ping=True` so a container restart doesn't kill the next request). `docker-compose.yml` runs it locally on host port **5433**; production uses a managed instance. `SQL_ECHO=1` turns statement logging on for debugging — leave it off in production, since it logs member emails and PSIDs.
- **`--workers 1` is still a correctness requirement, but for only one reason now:** slowapi keeps rate-limit counters in **process memory**, so N workers makes every limit N× looser, non-deterministically. Nothing warns you. Moving off SQLite removed the second reason (one file, single-attach volume). Multiple workers become viable once the limiter is Redis-backed *and* the uploads volume is shared or moved to object storage.
- **A Railway volume attaches to exactly one service**, so a separate cron service cannot read `/data` — backups have to run in-process. It also means deploys are **not zero-downtime** (the old container must release the volume first). Don't deploy during an event.
- **Migrations run as a Railway pre-deploy command (`alembic upgrade head`), never at app startup.** No `cd` — the Dockerfile's `WORKDIR` is `/app` and `COPY . .` puts `alembic.ini`/`alembic/` right there, so the container's layout is flat, unlike the repo where they sit under `backend/`. That also satisfies `prepend_sys_path = .`, which needs the CWD to be the directory holding `database.py`. Migrations need `DATABASE_URL` only and never touch `/data`, so a pre-deploy container doesn't contend for the single-attach volume above. Since `create_db()` no longer creates tables, a deploy that skips the migration comes up **green** — `GET /health` doesn't touch the DB by design — and then 500s on the first real query. On a brand-new production database the order is: deploy → `alembic upgrade head` → `python bootstrap.py` (structure + seats), never `seed.py`.
- `GET /health` is the platform liveness probe and deliberately **does not touch the DB**, so a transient lock can't get a healthy container killed. `GET /health/db` is the manual readiness check.
- **`assert_production_config()` also requires all four `GDRIVE_*` vars** (via `drive_services.is_configured()`), so Drive is a **boot dependency in production** — set them in Railway *before* deploying, or the container won't start. It's presence-only, which is the right target: present-but-revoked credentials already fail safe (the API raises, delete returns `False`, the file id is kept), while *absence* is what silently orphaned resumes. See the dev-mode-no-op entry in "What NOT to do".
- `assert_production_config()` also rejects a CORS origin still containing `localhost`. Without that check a forgotten `CORS_ORIGINS` deploys **green** and then fails every browser call with an opaque CORS error that leaves nothing in the server logs.
- **Production serves no API schema.** `docs_urls()` in `main.py` returns `None` for `docs_url`/`redoc_url`/`openapi_url` under `ENVIRONMENT=production`, and the result is splatted into the `FastAPI(...)` constructor. It's a function (mirroring `cors_origins()`) purely so tests can monkeypatch `ENVIRONMENT` and call it directly — the value itself is necessarily read at **import** time, since `FastAPI()` is constructed at import, which is the one place the `ENVIRONMENT` switch can't be read at call time like everywhere else. `main.py` therefore calls `load_dotenv()` itself rather than relying on `database.py`'s import side effect.
- **CORS is an exact-origin allowlist with no regex** — see the comment above `add_middleware` in `main.py` and the "What NOT to do" entry. Preview deployments consequently cannot call the production API; add the exact origin to `CORS_ORIGINS` if one ever needs to.
- **Secrets on disk that must never enter an image:** `backend/.env`, `backend/secrets/*.json`, and the leftover pre-Postgres `database.db` / `database.db.bak-*` files all still exist locally and are gitignored — invisible to a Git-triggered build, but copied verbatim by a local `docker build` / `railway up`. `backend/.dockerignore` is what prevents that. The old `database.db` still contains every seeded admin account sharing `password123`, so it stays excluded until it's deleted.
- Google Sheets credentials support `GOOGLE_SERVICE_ACCOUNT_JSON` (one-line JSON via `jq -c .`) for deployment, falling back to the `CREDENTIALS` file path for local dev. The autouse `disable_event_tracker_sync` fixture clears **both**.

## Key Rules & Lessons Learned

### Never commit secrets
- `backend/.env` and `frontend/.env.local` must stay out of git
- These should already be in `.gitignore` — verify before any commit

### Backend patterns
- Always use `SessionDependencies` (from `services/dependencies.py`) for DB sessions — do not create sessions manually
- Normalize emails with `normalize_email()` from `validators/email.py` before any DB lookup or insert
- New routes go in an APIRouter under `routes/` (included in `main.py`); new DB models go in `models/` and must be imported in `database.py` — that import is the only thing that registers the table in `SQLModel.metadata`, which is both what Alembic autogenerates from and what the test suite builds its schema from, so forgetting it leaves the table silently missing from migrations *and* from every test
- Use `utcnow()` from `services/time_services.py` for "now" — `datetime.utcnow()` is deprecated and raises DeprecationWarning on Python 3.12
- Tests live in `tests/<area>_tests/`; run with `.venv/bin/python -m pytest tests/` from `backend/` — **the Postgres container must be running** (`docker compose up -d` from the repo root) or every test fails to connect. API tests use the `client` fixture from `tests/conftest.py` (dedicated `shpe_test` Postgres database + auth override); `httpx` is required for TestClient
- Passwords are hashed with `get_password_hash()` from `security/hashing.py` — never store plaintext

### Frontend patterns
- All API calls go through the `api` axios instance in `src/api/api.js` — never use fetch or a raw axios import
- Pages live in `src/pages/`, reusable UI in `src/components/`
- Routes are defined in `App.jsx` — update there when adding new pages
- **Every page calls `useDocumentTitle` once, near the top of the component.** `index.html` carries one static `<title>` for all 19 routes, so a page that skips the hook silently inherits whichever title the previously-visited page set — wrong in the tab, in browser history, and in bookmarks. `useDocumentTitle("Calendar")` → `"Calendar | SHPE UH"`; a bare `useDocumentTitle()` → the full site title, used **only** by `home.jsx` (`"Home | SHPE UH"` reads worse than the brand title on the landing page). Pages whose title depends on fetched data pass a fallback rather than a falsy value (`useDocumentTitle(product ? product.name : "Shop")`), so the tab doesn't flash the site default mid-load; `shop-order.jsx` sidesteps that entirely by titling from the `code` route param, which is available before the lookup resolves. The hook deliberately does **not** restore the previous title on unmount — every route sets its own
- The About page (`pages/about.jsx`) has its **own hardcoded** 2026-2027 E-Board + Chairs roster (names/positions/emails). This is **separate from and not synced with** `chapter_data.py`'s `COMMITTEE_ROSTER` **or with role assignment** — editing one does NOT update the others, and they can drift (the About chairs use committee role-based `@shpeuhchair.org` emails, while seed users use `<first>.<last>@cougarnet.uh.edu`). Promoting someone to a chair role via `/members` updates the Committees page only; About stays stale until hand-edited (see "President role & chapter admin" — this is deliberate, since About is public and `/committees` requires auth). Cards fall back to an initials placeholder when a member has no `img`, and the email line is omitted when `email` is empty.
- Tailwind v4 is used — do NOT use v3 syntax (e.g. `bg-[color]` utilities are fine, but config is in `tailwind.config.cjs`)
- The home page (`pages/home.jsx`) `#insta` grid is wired to a live **Behold** (behold.so) Instagram feed: a `useEffect` fetches `VITE_BEHOLD_FEED_URL` on mount, takes the first 6 `data.posts`, and renders each as an `<a>` (permalink, new tab) wrapping an `<img>`. Image src is `post.sizes?.medium?.mediaUrl` (Behold-hosted thumbnail) with `post.mediaUrl` (Instagram CDN) as fallback. This is an **external public CDN** — it uses `fetch()` directly, NOT the `api.js` axios instance. On fetch error / unset env var, `instaPosts` stays empty and the original shimmer placeholder renders as fallback so the layout never breaks.

### Styling
- The design-system tokens live in `src/styles.css` `:root` — brand colors (`--shpe-navy`, `--shpe-blue`, `--shpe-red`, `--event-*`), gradients (`--gradient-navy`, `--gradient-orange`), radii (`--radius-*`), shadows (`--shadow-card/pop/modal`), and container widths. Reference these tokens (in Tailwind arbitrary values or inline styles) rather than hardcoding hex. Legacy aliases `--blue`/`--navText`/`--muted` are kept for existing pages.
- Work Sans (the brand typeface) is loaded via a Google Fonts `@import` at the top of `styles.css` and set as the `body` font (`--font-body`) — don't re-import it per page.
- Use Tailwind utility classes first; only add custom CSS to `styles.css` when Tailwind can't do it (e.g. the header member-dropdown classes). `App.css` is unused Vite boilerplate — don't add to it.
- Shared button classes: `.primaryBtn` (navy), `.accentBtn` (SHPE red), `.ghostBtn` (outline).
- Framer Motion is available for animations — use it for page transitions and reveals

### What NOT to do
- Do not use `python-jose` — the project uses `pyjwt` (imported as `jwt`)
- Do not add `python-dotenv` to requirements — it is already a transitive dependency; just call `load_dotenv()` at the top of any file that needs env vars
- Do not create new axios instances — reuse the one in `api/api.js`
- Do not use `React.useState` / `React.useEffect` — use named imports: `import { useState, useEffect } from 'react'`
- Do not call setState synchronously inside a `useEffect` body — the lint config (react-hooks/set-state-in-effect) fails the build. For "reset state when a prop/route param changes" or "prefill once async data arrives", use the render-phase adjustment pattern (compare-and-set during render, like `Header.jsx`'s `prevPath` and `shop-checkout.jsx`'s prefill)
- Do not export helpers/constants from a file that also exports a React component — react-refresh lint fails. Put shared helpers in `utils/` and components in their own files (this is why `StatusPill` is its own component and `utils/shop.js` has no JSX)
- The lint config's `no-unused-vars` only ignores identifiers matching `^[A-Z_]`, and usage inside JSX (like `<motion.div>`) doesn't count — so any file importing lowercase `motion` from framer-motion needs `/* eslint-disable no-unused-vars */` at the top (Header.jsx, profile.jsx, members.jsx all do this)
- Do not put digits (or other symbols) in seeded/test user names — `UserCreate`'s name validator allows only letters, hyphens, apostrophes, and spaces, so a first_name like `Test1` crashes `seed.py` mid-run. Put distinguishing digits in the email instead (that's why the unpaid test member is "Test Unpaid" / `test1@cougarnet.uh.edu`)
- Do not put a privilege- or state-bearing field on `UserBase` — it's inherited by `UserCreate`, so anything there is settable from the public `POST /signup` body. This actually shipped: `role` and `points` lived on `UserBase` and a plain signup POST with extra `"role": "President"` / `"points": 999999` keys created a fully-admin account with an inflated point total, reachable from `/docs`'s "Try it out" with no auth. Fields like these belong on the `User` **table model** instead, next to `email_verified`/`password_changed_at`/`hashed_password` — and if `UserOut` still needs to expose them publicly, it must re-declare them explicitly (pydantic's default `extra='ignore'` means a field UserOut doesn't re-declare just silently vanishes from `/me`, no error). `services/user_services.create_user` now takes `role` as an explicit keyword argument (defaults to `Role.member`) instead of reading it off the parsed schema — seed.py's privileged seeders (`seed_committees_and_chairs`, `seed_comm_director`, `seed_president`, `seed_eboard`) pass it explicitly; `/signup` never does, so every signup lands as a plain member regardless of what the request body contains.
- Do not query the database by a role's **display value** — SQLModel persists a Python enum by its **name**, while Pydantic serializes it by its **value**, so the same role reads differently at each layer. `Role.president` is stored as `president` and returned by the API as `"President"`; `docker compose exec db psql -U shpe -d shpe -c "SELECT * FROM \"user\" WHERE role='President'"` matches **zero rows and reports no error**, which looks exactly like "that account doesn't exist". Use the enum name in SQL (`WHERE role='president'`, `'comm_director'`, `'academic_chair'`) and the display string only when comparing against API output — that asymmetry is why `utils/shop.js`'s `SHOP_ADMIN_ROLES` holds `"Communication Director"`-style strings while the backend's holds `Role` members. Also note: `user` and `order` are reserved words in Postgres — any raw psql query against those tables needs escaped double quotes (`\"user\"`, `\"order\"`), unquoted `user`/`order` is a syntax error
- Do not trust `alembic revision --autogenerate` to notice a changed **enum**. SQLModel maps `Role`, `Classification`, `OrderStatus`, etc. to real Postgres `CREATE TYPE ... AS ENUM` types, and autogenerate does not compare enum *members* at all — adding a `Role` value produces a revision whose `upgrade()` body is `pass`, which then applies cleanly and changes nothing. The symptom appears far from the cause: the role exists in Python, `/admin/roles` offers it, and the first write of a row carrying it fails with `InvalidTextRepresentation`. Write the DDL by hand in the revision: `op.execute("ALTER TYPE role ADD VALUE 'new_chair'")`. Two caveats — on Postgres 12+ that statement may run inside a transaction but the new value **cannot be used** by later statements in that same transaction, so a backfill that writes rows with it belongs in a separate revision; and `ADD VALUE` has no inverse, so `downgrade()` must either recreate the type wholesale or be left an explicit, commented no-op. This is the same native-enum trap documented under the reseed procedure — Alembic makes it quieter, not safer
- Do not add a seeder without an "already seeded" guard — `seed.py` is re-run to top up new data, so an unguarded one duplicates its rows every time. `seed_events` shipped without one and had quietly accumulated 5 copies of all 3 sample events before anyone looked. Guard on the rows that seeder owns (`seed_events` filters `source_row_id IS NULL`, so sheet-synced events can't mask it), and remember the flip side: a guard means editing the seed data in the file does nothing to an existing db until you clear those rows first
- Do not add a new seeded account without setting `email_verified = True` on it after `create_user()` — `/login` 403s unverified accounts, so the account seeds fine and then silently can't log in. This bit the seeded president: the email-verification feature and the president seed were developed on separate branches, so the merge was textually clean and left `seed_president` as the one seeder missing the flag. Any seeder added while a branch is out of date needs the same check
- Do not guard a destructive script on an ambient flag when the destructive property is the **connection target**. `seed.py`'s original sole guard was `ENVIRONMENT=production`, but `ENVIRONMENT` has nothing to do with which database the script writes — that comes from `DATABASE_URL`, resolved independently in `database.py`. The two are never correlated, and `ENVIRONMENT` is documented as "leave unset for local dev", so the blind spot was the default state of every dev machine: export a production `DATABASE_URL` for a `psql` session or an `alembic upgrade head` (the README's own reseed procedure runs that and `seed.py` back to back), leave `ENVIRONMENT` unset, and the guard passes while ~30 accounts sharing `password123` — including an `email_verified` president — land in the live database, with no log line distinguishing them from real ones. `assert_local_database()` in `database.py` now guards the causal property: it parses `DATABASE_URL` with `make_url` and refuses unless the host is loopback (the load-bearing half — a managed instance is never reachable on localhost) **and** the db name is `shpe`/`shpe_test`. Both guards stay; they catch different mistakes ("I'm on the prod box" vs. "I exported a prod URL locally"). Deliberately **no bypass env var** — a flag that waves it through would recreate the exact defect. Note the mirror-image rule for `bootstrap.py`: it is *meant* to run against production, so it must never get this guard (its safety is structural — it can't create an account at all)
- Do not add a delete/sweep pass to `sync_events` — the duplicate left behind by a rescheduled event is intentional (see "Event tracker sheet sync"); deleting silently kills reminders and resets points
- Do not hard-delete a shop `Product` (and do not unlink its image when retiring) — `DELETE /shop/products/{id}` is a **soft delete**; destroying the row breaks restore and throws away the image a restore needs (see "Merch shop")
- Do not pair `.catch(() => {})` with a success toast in the frontend — the user sees "saved" when nothing saved. Surface `err.response?.data?.detail` via `showToast` like `saveProduct`/`retireProductRow` do
- Do not enforce a cart rule on the page that happens to trigger it — put it in `CartContext.addItem`. There are several entry points (product page, storefront, `MyOrders` re-order) and a per-page check silently misses the next one added. Note `CartProvider` now calls `useAuth()`, so **it must stay nested inside `AuthProvider`** in `main.jsx`; swapping the provider order throws on render
- **Do not display a money figure the server didn't just confirm.** Cart lines snapshot `priceCents` at add-to-cart time and persist to localStorage indefinitely (the existing-line branch only bumps `qty`), while `POST /shop/orders` recomputes the total from live catalog rows and charges **that** — the client sends no prices at all. So a $15 tee added before an admin raised it to $45 rendered "Pay $15.00" **and put $15.00 in the Apple Pay / Google Pay sheet**, which is the card networks' consent surface; the buyer approved one amount, was charged another, and first saw the real total on the confirmation page. Note the *attacker* direction was already closed by the same asymmetry (a forged localStorage price changes only the display), which is exactly why this read as safe. `CartContext.repriceCart()` now re-matches the cart against `GET /shop/products` on checkout mount and on drawer open, `PriceChangeNotice` shows old → new, and Pay stays disabled until the buyer acknowledges. Three things are load-bearing if you touch it: `reconcileCartLines` **returns the same `lines` array reference when nothing changed** (shop-checkout's Square effect depends on `subtotalCents`, and a needless change remounts the card iframe under a buyer mid-typing); the re-price runs during the **contact** step with `Continue to payment` disabled while it's in flight, which is what guarantees `subtotalCents` can't move once the card is mounted; and it **fails open** (`repriceState = "failed"`, checkout still works) because the backend is authoritative anyway and a network blip must not close the shop. `subtotalCents` also **excludes lines flagged unavailable** — they can't be purchased, so counting them would display a total that can never be charged, reintroducing the same divergence one level down
- Do not write a ref during render in this frontend — the lint config's `react-hooks/refs` rule fails the build on `someRef.current = value` at the top level of a component. `CartContext`'s `linesRef` is seeded by `useRef(lines)` and kept current inside the existing `[lines]` effect instead
- Do not expect a `<Link to="/page#anchor">` to scroll anywhere — React Router changes `location.hash` but never scrolls. The target page needs its own `useEffect` calling `scrollIntoView` on the hash (see `pages/profile.jsx` for `#orders`)
- Do not put a multi-step wizard's steps in one `<form>` without guarding the submit handler by step — Enter in any text input submits the whole form, POSTing a half-filled payload (see "Signup form"). Guard with `if (step < LAST) { nextStep(); return; }`
- Do not validate a signup field only on the backend. Anything `UserCreate` requires must also be checked in the matching step of `signup.jsx`, or the member fills in five steps and gets a 422 naming a field from step 4 (that's exactly how `country_origin` behaved)
- Do not use a Google **service account** to upload to a personal My Drive folder — Google 403s it (`storageQuotaExceeded`); use the OAuth refresh-token credentials instead (see "Google Drive resume sync")
- Do not call blocking I/O inside an `async def` handler — it runs **on the event loop** and freezes the server for *every* user, not just that request. This already bit twice: `send_email` (blocking `smtplib`) was called straight from `async def signup` and `async def request_password_reset`, and `authenticate_user` (argon2id, 64 MiB / ~100 ms) from `async def login_for_token`. Wrap them in `await asyncio.to_thread(...)` — `auth_routes.py`'s HIBP call is the pattern to copy. Note `smtplib.SMTP()` also defaults to **no timeout**, so one unresponsive mail host hangs the loop forever; `send_email` now passes `SMTP_TIMEOUT`
- Do not key rate limits on `request.client.host` (slowapi's default `get_remote_address`) once the app is behind a proxy — that address is the **proxy's**, identical for every visitor, so all four limits silently collapse into one global bucket (5 signups/hour for the entire chapter). `services/rate_limit.py`'s `client_ip` reads `X-Forwarded-For` and takes the **rightmost** entry: the leftmost is client-supplied and trivially spoofed. Same reason `--forwarded-allow-ips=*` is not a fix — uvicorn's `ProxyHeadersMiddleware` takes the leftmost
- Do not re-add `allow_origin_regex` to the CORS middleware, and do not "fix" a preview-deploy CORS error by reaching for one. Starlette matches that pattern with **`re.fullmatch`** (`middleware/cors.py`), so anchoring it as `^...$` is a **no-op** — the whole origin already has to match. What actually matters is breadth: `https://.*\.vercel\.app` (the value this README used to document as the example) matches every **other** person's Vercel project too, and `allow_credentials=True` is already set. It's survivable today only because auth is a Bearer token read from `localStorage`, which is origin-scoped, so an attacker's page can't reach a member's token — that stops being true the day auth moves to cookies. Add the exact origin to `CORS_ORIGINS` instead.
- **Do not register a route as `@router.get('/')` under a prefix — use `@router.get('')`.** `event_routes.py`'s list route was the only one in the codebase declared as `'/'`, giving it the full path `/events/` while the frontend, the tests, and every sibling route use `/events`. FastAPI's `redirect_slashes` papered over the mismatch with a **307**, so it worked locally, worked in the test suite (TestClient follows redirects), and worked under `curl -L` — and failed only in the browser, in production. The reason is the redirect's `Location`: uvicorn runs with `--proxy-headers` but **no `--forwarded-allow-ips`**, so it trusts forwarded headers only from `127.0.0.1`, Railway's proxy isn't that, `X-Forwarded-Proto: https` is ignored, and the app builds the redirect against scheme `http`. The browser gets `location: http://…/events/` from a page served over `https://www.shpeuh.com`, blocks it as **mixed content** before the request is ever sent, and axios reports a generic network failure — which lands in `calendar.jsx`'s `.catch()` as "Could not load events. Please try again.", a message that describes the API as unreachable when it was actually returning 200. Note how much this survives: the endpoint is fine, CORS is fine, `/health` and `/health/db` are green, and `curl` succeeds, so every check short of the browser's own console says nothing is wrong. Two rules follow — a redirect is not free when the client is a browser on another origin (it must re-pass CORS *and* the scheme check), and **path equality beats `redirect_slashes`**: declare the path callers actually use so no redirect is generated at all. The `''` form is what the other seven `/events/*` routes already do implicitly. The scheme half is now fixed at the source too — see the `ForwardedProtoMiddleware` entry below — so a future redirect survives; declaring the path correctly is still the first line of defence.
- **Do not fix a wrong request scheme with uvicorn's `--proxy-headers` / `--forwarded-allow-ips=*`** — `services/forwarded_proto.py` does it instead, and the Dockerfile deliberately passes neither flag. The tempting one-liner is `--forwarded-allow-ips=*` (the default `127.0.0.1` is why plain `--proxy-headers` silently did nothing behind Railway, while its Dockerfile comment claimed it fixed exactly the bug it was failing to fix). But uvicorn's `ProxyHeadersMiddleware` rewrites `scope["client"]` from the **leftmost** `X-Forwarded-For` entry as well as the scheme, and that entry is client-supplied. `rate_limit.client_ip` already ignores `scope["client"]` and parses the header rightmost for that reason — but it still *falls back* to `scope["client"]` when the trust flag is off or the header is missing. So enabling uvicorn's version silently converts that fallback from "every visitor shares the proxy's bucket" (too strict, **fails closed**) into "the caller picks their own bucket by sending a header" (no limit at all, **fails open**) — trading a visible outage for an invisible bypass of every rate limit in the app. `ForwardedProtoMiddleware` writes only `scope["scheme"]`, validates the value against `("http", "https")` so a junk header can't corrupt every generated URL, reads the **rightmost** entry like `client_ip`, and is gated on the same `TRUST_PROXY_IP_HEADERS` flag (imported from `rate_limit.trust_proxy_headers`, the single reader of that env var — do not add a second). It is registered **last** in `main.py` so it ends up outermost, correcting the scheme before the router's `redirect_slashes` reads it; being outside CORS is safe because it only edits the scope and never emits a response. `tests/test_forwarded_proto.py` pins all of it, including a downgrade attempt via a leading `http,` entry.
- **Do not set `VITE_API_URL` without a scheme, and do not read a white screen as a frontend bug.** `VITE_API_URL=shpe-uh-website-production.up.railway.app` (no `https://`) shipped to Vercel and white-screened `/calendar` and `/shop` while every static page rendered fine. Axios treats a schemeless `baseURL` as a **relative path**, so `GET /events` became `https://www.shpeuh.com/shpe-uh-website-production.up.railway.app/events` — a request that never leaves Vercel, matches `vercel.json`'s catch-all `/(.*)` → `/index.html` rewrite, and comes back as **`index.html` with a 200**. The 200 is the whole problem: both pages have correct `.catch()` branches and neither fires, because nothing failed. The component instead receives a large HTML **string** where it expected an array — `shop.jsx`'s `(products ?? []).map(...)` throws `products.map is not a function`, and `calendar.jsx`'s `for (const ev of events)` silently iterates the string *character by character* (strings are iterable, so the loop itself is fine) before dying on `a.start_time.localeCompare(...)` against `undefined`. Either way React unmounts the tree and the page goes blank with the real cause only in the browser console. Home and About survive because they never touch this API (the Instagram grid uses a raw `fetch()` with a full URL), which makes the failure look page-specific rather than global. Two generalizations worth keeping: **an SPA catch-all rewrite turns every misrouted API call into a 200**, so on a Vercel-hosted SPA a wrong `baseURL` can never surface as a network error the way it does locally; and `import.meta.env.*` is inlined at **build** time, so fixing the variable in the Vercel dashboard changes nothing until a **rebuild with the build cache disabled** — a redeploy that reuses the cache reproduces the identical bundle and looks like the fix didn't work. Confirm the deployed value directly rather than trusting the dashboard: `curl -sL https://<site>/assets/index-*.js | grep -o 'baseURL:[^,}]*'`.
- **Do not put the frontend's domains in `ALLOWED_HOSTS`.** It gates the `Host` header of requests arriving **at the API**, which is the Railway hostname (or a custom `api.` domain) — never `shpeuh.com`/`www.shpeuh.com`, however natural that guess feels next to `CORS_ORIGINS` in the same variable list. Setting it to the frontend domains makes `TrustedHostMiddleware` reject **every** request with a bare `400 Invalid host header`, including `GET /health` — which is upstream of every route, so the platform liveness probe fails too and the "deliberately does not touch the DB" property buys nothing. The symptom is maximally misleading: the API is up, the container is healthy, `CORS_ORIGINS` is correct and the 400 still carries the right `access-control-allow-origin` header (CORS is outermost by design), so every check short of reading the response body says the backend is fine. Diagnose with `curl -s https://<api>/health` and read the **body**, not the status. The variable is optional — unset skips the check entirely, which is the right move if there's any doubt.
- Do not read `ENVIRONMENT` (or `SQUARE_ENVIRONMENT`) with a bare `os.getenv` — call `config.is_production()` / `config.square_is_production()`. This shipped: four call sites each read `ENVIRONMENT` themselves and **two forgot to `.strip()`**, which split the app cleanly along the line between the signals an operator checks and the two controls that enforce payment. `docs_urls()` and `seed.py` stripped; `assert_production_config()` and `charge_card()` did not. Set `ENVIRONMENT="production "` in the Railway dashboard — a pasted value, the most ordinary way an env var goes wrong — and: the startup gate returns without validating anything, so the app **boots green with no Square credentials**; `charge_card` takes the dev-mode branch and returns `None`; and `shop_routes.py`'s `if square_services.is_configured() and not payload.payment_token` never even demands a card, because `is_configured()` is false. Every checkout then persists with `square_payment_id=None`, `Order.status` defaults to `paid`, a receipt email goes out, and `has_paid_dues` flips true — **merch ships and dues are marked paid with no money collected**. The reason it's so quiet is the *other* half of the split: `/docs` still 404s and `seed.py` still refuses, so both things anyone would check to confirm production mode report success. There is no log line and no failed health check; the only symptom is zero revenue in Square, noticed weeks later. Note the asymmetry — the `SQUARE_ENVIRONMENT` half of the same bug failed **closed** (a padded value made the gate demand `SQUARE_ENVIRONMENT=production` when it had been set), which is why that one would have been found immediately and the `ENVIRONMENT` one was not. `tests/test_deployment_config.py::test_padded_environment_still_enforces_the_gate` and `tests/shop_tests/test_square_payments.py::test_unconfigured_square_refuses_to_simulate_in_production` pin both halves; each fails if a call site starts reading the raw env var again.
- **Do not let a dev-mode no-op return the same value as success when the caller uses that value to discard state.** Both Drive functions have an unconfigured branch, and only one of them can be a silent no-op. `upload_resume_to_drive` returns `None`, the caller guards with `if drive_file_id is not None`, and skipping does nothing — the old id survives, so it fails safe. `delete_resume_from_drive` used to return `True`, and its caller reads `True` as "the Drive copy is gone" and **nulls `resume_drive_file_id`** — the only handle anything has on that file, since the `drive.file` scope means the app can never list or re-find a file whose id it forgot. So an instance that lost its `GDRIVE_*` vars (a redeploy, a rotated OAuth client) answered every deletion request with 204 while the PDF — full name, PSID, phone, work history — stayed in the folder shared outward. The vicious part is that it's **self-concealing**: restore the credentials and retry, and the function returns `True` at the `not file_id` branch — correctly, because the row now says there is no Drive copy. Fixing the root cause does not fix the outcome; cleanup is a human in the Drive UI. Nothing detected it either, since `assert_production_config` checked Square and SMTP but no `GDRIVE_*` var, so the instance booted green with only a `print()` saying "*would* delete Drive file …". Both halves are now closed — the unconfigured branch returns `False` (leaving `resume_filename IS NULL AND resume_drive_file_id IS NOT NULL`, a *queryable* orphan rather than a silent one) and `is_configured()` is in the boot gate. General rule: a no-op's return value must be distinguishable from success whenever success is load-bearing. `test_delete_without_drive_config_reports_failure_so_the_id_is_kept` and `test_drive_config_dropped_after_upload_keeps_the_pointer` pin it — and note the *original* test asserted `is True` under the name `..._reports_success`, so this shipped looking deliberate.
- Do not expose the API schema in production, and do not disable only `/docs` — `/docs` and `/redoc` are just renderers for `/openapi.json`, so leaving the schema up means the interactive console is one paste into any Swagger instance away. All three are gated together by `docs_urls()`. The schema is generated from real code, so it lists every path, every model field, and which endpoints need auth; the `role`/`points` privilege-escalation bug (above) was reachable through `/docs`'s "Try it out" button, which is exactly the reconnaissance this removes
- Do not size rate limits for a single user. At a GBM most attendees share **one public IP behind campus NAT**, so a per-IP limit tuned for one person starves the whole room. The limits are env-tunable (`RATE_LIMIT_*`) and default high on purpose; the controls that actually stop abuse are per-**account** (email verification, HIBP check, 10-attempt lockout) and NAT can't defeat those. Tests derive their loop counts from the constants via `limit_count()` rather than hardcoding — don't reintroduce a magic number
- **Do not give the buyer a decline message that says *which* check the card failed**, however much more helpful "the CVC didn't match" is than "your card was declined". `POST /shop/orders` is anonymous by design (`get_optional_user` returns `None` rather than 401ing) and the frontend bundle ships `VITE_SQUARE_APP_ID`, so anyone can tokenize a stolen card with Square's own SDK and POST it. `_DECLINE_MESSAGES` used to map eight Square codes onto five distinguishable strings, which let a caller sort a stolen-card list — bad number vs. live-card-wrong-CVC vs. live-card-wrong-ZIP vs. live-but-broke vs. a 201 — against the chapter's **live merchant account**, at `ORDER_LIMIT`'s 60/minute. The loss isn't data: it's a per-chargeback fee on every card that goes through and a fraud ratio that gets a small merchant's Square account frozen, i.e. no dues collection and no merch sales, discovered weeks later as zero revenue. `_DECLINE_CODES` is now a **set**, and `_buyer_message()` has exactly **two** outcomes: every decline reads `_DECLINED_MESSAGE`, everything else (a Square outage, an `UNAUTHORIZED` token) reads `_GENERIC_MESSAGE` — that split is kept only because telling a member their card was declined during *our* outage sends them to their bank for nothing, and it leaks nothing, since a carder's probes come back as decline codes either way. The specific code stays in the server log (`logging.warning` for a decline, `logging.exception` otherwise), which is what a member calling to ask why their card failed is actually answered from. `test_every_decline_code_returns_one_identical_message` pins this; if it fails, the oracle is back
- **The failed-charge budget is the second half of that fix, and it is not `ORDER_LIMIT`.** `FAILED_CHARGE_LIMIT` (`RATE_LIMIT_FAILED_CHARGE`, 10/10 minutes) is spent **only by a declined charge** — `failed_charge_budget_exhausted()` checks before the charge, `record_failed_charge()` spends inside the `PaymentError` handler. That asymmetry is the whole reason it can be tight enough to matter while `ORDER_LIMIT` stays at the generous NAT-sized 60/minute: a real dues drive generates successful charges, so ten separate *failed* cards from one IP in ten minutes is already anomalous. Note it is **not** a `@limiter.limit` decorator — that counts every request to the route and slowapi has no `deduct_when` — but it is built on `limiter.limiter.test()`/`.hit()` rather than a hand-rolled dict, so it shares the limiter's storage and conftest's autouse `limiter.reset()` isolates it between tests for free. Both `PaymentError` flavors spend it, including the infrastructure-generic one: during a Square outage an IP burns through in ten tries, but checkout is already broken then, and letting an attacker pick a failure that costs nothing hands the probe loop straight back
- **Do not let a "already in this state" branch fall through into the side effects.** `join_committee` handled a repeat join by re-setting `status = True` and then continuing — the `if existing_membership: ... else: ...` chose whether to *create* a membership, and both branches fell through to the unconditional welcome `Notification` plus one per chair. The membership table looked perfect (one row, unchanged, roster normal); the notification table grew by 3 rows on every POST, from any verified member, against any committee's chairs. Three properties made that permanent rather than merely noisy, and it is the combination that matters: the route had **no rate limit** at all, **nothing anywhere deletes a `Notification` row**, and `GET /notifications` returns a member's entire history with **no LIMIT** while `dashboard.jsx` fetches and renders all of it on every mount. So the attacker stops and the chair's dashboard stays broken — the real "X joined your committee" signal is gone for good, and cleanup is raw SQL. Note the early return alone does **not** close it: `leave_committee` **hard-deletes** the membership row, so `join → leave → join` recreates the "no existing membership" condition every iteration and the early return never fires; that bypass costs 2 requests per 3 rows, i.e. nothing. The per-account `JOIN_LIMIT` above is what actually bounds it, and the ordering inside the route is load-bearing — the early return sits **above** the budget check so a no-op join spends nothing, and `record_join` fires only after a join that really wrote notifications. Reverse those two and a member who has spent their budget gets a 429 for re-clicking Join on a committee they are already in. `tests/committee_tests/test_join_idempotence.py` pins every half of this. Still open from the same finding: `GET /notifications` is unpaginated and there is no retention policy, so a feed flooded before this fix stays flooded
- **Do not enforce a visibility flag only on the read path.** `Committee.joinable` was documented as "not committees members can join" and implemented as one `WHERE` clause in `get_all_committees` — i.e. members can't *see* them, a much weaker claim. `join_committee` resolved through `get_committee_or_404` (a bare `session.get`, no predicate) and inserted a membership with no check beyond authentication, so any verified member could `POST /committees/15/join` … `/24/join` and self-insert into the ten hidden E-Board rows. The ids aren't even guesswork: `seed.py` creates the 14 real committees before the 10 E-Board rows, so they're contiguous at 15-24, and `GET /committees` hands out 1-14 as the map. The payoff was `GET /committees/{id}/messages`, gated on exactly `is_active_member` — a self-inserted row is byte-identical to a legitimate one, so the member read every officer broadcast in that container and got a notification preview for each future one. **The frontend is never the boundary**: the id is a bare path int, and a member's own JWT sits in their own `localStorage`, so this needs no stolen credentials and no XSS — just curl. Same shape as the `role`/`points`-on-`UserBase` bug above (unreachable from the signup form, reachable from a POST body); the difference is that one was a field nobody rendered and this was a row nobody listed. Two further generalizations worth keeping: **a write-path check is prospective only when a read gate keys on the row it creates** — refusing new joins does nothing about rows already in the table, which is why the message gate had to be fixed too rather than just `join_committee`; and **a legitimate flow can keep minting the shape you just banned** — `_sync_chair_memberships`'s demote branch clears `is_chair` but leaves `status=True`, so every election leaves an ex-officer holding an active non-chair row on their old E-Board seat, indistinguishable from a forged one. That's precisely why the fix is a gate on read rather than a cleanup query: there is nothing in the row to tell the two apart. `tests/committee_tests/test_joinable_enforcement.py` pins it
- **QR check-in is the extreme case of the above** — its entire premise is a few hundred people scanning within minutes from one room on one network. `/events/attend` originally shipped at `20/minute` per IP, i.e. ~20 check-ins per minute for the whole GBM with everyone else getting a 429 at the door. It now uses `ATTEND_LIMIT`/`CODE_PREVIEW_LIMIT` (600/minute). This is safe because the endpoint's real guards are per-account: it requires a valid JWT, and `EventAttendance` is keyed `(user_id, event_id)`, so a repeat scan returns "already recorded" and awards no points (`record_sign_in` checks for the row and catches the `IntegrityError` from two scans racing). Don't tighten these back toward a per-person number
- Do not enforce an upload size cap **after** `await file.read()`, and do not assume an auth dependency protects an upload route from a large body. Both upload handlers used to read first and check `len(contents)` second, which is too late twice over. `read()` with no argument copies the whole upload into one `bytes` object, so a multi-gigabyte POST lands in resident memory before the 413 — and `--workers 1` means that process is the entire API, so it's an OOM kill of the whole site, repeatable by any verified member. Check `file.size` instead: Starlette's parser maintains it as it writes (`starlette/datastructures.py`), so it's exact and costs nothing. The deeper half is **not reachable from a handler at all**: FastAPI parses the multipart form **before** it solves dependencies (`body = await request.form()` runs well above the `solve_dependencies` call in `fastapi/routing.py`), and the parser's `max_part_size` is applied only to non-file parts — a part carrying a `filename` gets a `SpooledTemporaryFile` with **no upper bound**. So the body is fully written to the container's temp storage before `get_current_user` (or `require_shop_admin`) ever runs, i.e. anonymously. That's what `BodyLimitMiddleware` (`services/body_limit.py`) is for; the per-route `file.size` checks are the second layer, not the first
- Do not give `BodyLimitMiddleware` its 413 via `app.add_exception_handler` — it must own the response itself, which is why it suppresses the app's send after the cap is blown. FastAPI wraps form parsing in a broad `except Exception` that re-raises **everything** as `HTTPException(400, "There was an error parsing the body")` (`fastapi/routing.py`), so cutting the stream off mid-parse trips that clause and a registered handler never sees the exception. The DoS is prevented either way — the failure mode is purely that the client is told its request was malformed rather than too large. This was invisible to the isolated middleware tests (a route with no `File` body_field never enters that try block) and only showed up against a live server; `tests/test_body_limit.py::test_chunked_upload_over_the_cap_returns_413_not_a_parse_error` is the regression test, and it goes through `/me/resume` specifically because the route shape is what triggers it
- Do not hardcode a rate-limit count in a test — import the constant and use `limit_count()`, or retuning a limit breaks unrelated tests (this caught three)
- Do not create a second user in a test by overriding only `cougarnet_email` — **`personal_email` and `psid` are unique too**, and `make_user`'s defaults are the same literals every call, so the second insert dies on `ix_user_personal_email` with a raw `IntegrityError` that names a field the test never mentioned. Vary all three (`test_bootstrap.py`'s local `member(session, local_part)` helper derives all three from one string and is the pattern to copy)
- Do not give product images a deterministic filename. They're served with `Cache-Control: immutable`, so reusing `product_<id>.<ext>` would make every browser and CDN serve the **old photo forever** after a replacement. `upload_product_image` appends `secrets.token_hex(4)`; `productImageUrl` mirrors it with `?v=<image_filename>`
- Do not call `PasswordHash.recommended()` per hash — it builds a fresh argon2id hasher every time. `security/hashing.py` holds one module-level instance

## Site metadata & branding
- **All of this is generated from one source asset:** `src/assets/logos/shpeMark.png` (the SHPE pinwheel, 709×708, transparent). Everything in `public/` was produced from it by a one-shot Pillow script; **Pillow is deliberately not a project dependency** (not in `requirements.txt`, not in `package.json`) — it ran in a throwaway venv and only the output PNGs are committed. Regenerate only if the mark itself changes.
- **Transparency differs per icon on purpose.** `favicon.ico` (16/32/48 multi-res) keeps the mark's alpha so it reads on both light and dark tab bars. `apple-touch-icon.png` ships an **opaque white** background because iOS composites transparency onto **black**, which would put the navy/red arms on a black square. `icon-192/512.png` match it for consistency in PWA contexts.
- **The four absolute URLs in `index.html` are the one thing that breaks on a domain change** — `canonical`, `og:url`, `og:image`, `twitter:image`, grouped in a single commented block at the top of `<head>` so they're changed together. They can't be relative: link-preview scrapers don't reliably resolve relative paths, and the failure is silent (a card renders with no image, and nothing errors). Facebook's Sharing Debugger both previews the card and force-refreshes a stale scrape.
- **`index.html`'s `<title>` and `useDocumentTitle`'s `DEFAULT_TITLE` are the same string in two places** — the first is what a crawler and a cold load see before React mounts, the second is what `home.jsx` restores on a client-side navigation back to `/`. Change one and the tab title flickers between two values on the landing page. There is no build-time check for this.
- `robots.txt` disallows the member-only routes, the two token-bearing routes (`/verify-email`, `/reset-password`), and `/shop/checkout` + `/shop/order/`. This is tidiness, not a control — those pages are client-rendered behind `PrivateRoute` and the backend guards the data regardless.
- **Apple Pay's domain-association file goes in `public/.well-known/`** (see "Merch shop"). That directory now exists, so the file is a drop-in; Vercel serves static files before the SPA rewrite in `vercel.json`, so the catch-all `/(.*)` → `/index.html` doesn't swallow it.

## Production bootstrap (`bootstrap.py`)
- **`seed.py` refuses to run against a production database, and it is the ONLY thing that creates committees.** So a fresh production database is not merely sparse, it's unusable: no president means nobody can reach `/admin/*` to assign the first role (permanent lockout); no `Committee` rows means `sync_events` can't resolve `Role -> Committee.id`, writes no `EventHost` rows, and **QR check-in silently does nothing for everyone**; no `"T-Shirt Dues"` product means `startDuesCheckout` finds nothing by name and drops a freshly-verified member on the home page. `bootstrap.py` exists to fill exactly that gap.
- **The safety property is structural, not a flag: `bootstrap.py` never imports `create_user` and contains no password string.** It cannot create an account however it is run, which is *why* it correctly has no `ENVIRONMENT=production` refusal (the one in `seed.py` exists because seed mints ~30 accounts all sharing `password123`). Keep it that way — if it ever needs to make a user, that belongs in a different script with different guarantees.
- **`chapter_data.py` is the shared source and the reason it exists.** `bootstrap.py` *cannot* import from `seed.py` — seed's module-level `sys.exit(1)` fires on import under `ENVIRONMENT=production`. Copying the roster instead would mean a 15th committee has to be edited in two files, drifting silently (the same failure the About page already has). `chapter_data.DUES_PRODUCT` takes its name from `shop_services.DUES_PRODUCT_NAME` rather than a literal, so a rename can't half-apply. Chair *names* stay in `COMMITTEE_ROSTER` but `bootstrap.py` ignores that 4th tuple element — production chairs sign up and get promoted via `/members`.
- **Structure creation always runs and is idempotent** (guards mirror seed.py's). `ensure_structure` skips wholesale once any `RoleReport` exists, so re-running never stomps Structure-tab edits. It creates only the dues product — real merch goes in through Shop Manager.
- **`bootstrap.py` deliberately does NOT call `create_db()`.** `create_db()` does `RESUME_DIR.mkdir()`, and under `railway run` (prod env vars injected into a *local* process) `DATA_DIR=/data` would try to mkdir `/data` on the laptop. It assumes the app booted once and catches `sqlalchemy.exc.ProgrammingError` to print a "start the backend first" message. **Prefer `railway ssh` over `railway run`** for the same family of reasons. Note the `sys.stdout.flush()` before that stderr write — without it the error prints *above* the progress lines it's meant to follow.
- **`--president` / `--vpe` / `--vpi` are per-seat and ONE-SHOT with no override.** Each requires an existing, `email_verified` account; each refuses if anyone already holds that seat (if the holder *is* the target it's a success no-op, so re-running a command isn't a failure). Flags are processed independently so one bad email doesn't block the others. Exit code 1 if any seat went unfilled.
- **Why one-shot is the actual control, and what it is NOT.** Anyone who can run this already has Railway access → `DATABASE_URL` (raw SQL) and `SECRET_KEY`. With `SECRET_KEY` they can forge a JWT for any account (`security/jwt.py`, `dependencies.py` validates `sub` + signature) leaving **no database trace at all** — strictly stealthier and more powerful than this script. So hardening the script buys nothing against that threat; don't add password prompts or bootstrap tokens thinking it does. What one-shot *does* buy: once a seat is filled, every later change must go through `/members`, where `_assert_may_assign` stops even a VP from moving a top-tier seat. Break-glass recovery is deliberate raw SQL — possible, but impossible to mistake for routine. **The real perimeter is 2FA on Railway/GitHub/Google**, not this file.
- `promote()` reuses `_sync_chair_memberships` from `admin_routes` (imported *inside* the function, so the structure-only path doesn't pull FastAPI in). Redundant for the president, who bypasses every chair check, but it leaves the DB in exactly the state `/members` would have produced.
- **`notify_role_change` in `services/user_services.py` is shared by `bootstrap.py` and `PATCH /admin/members/{id}/role`.** It emails every sitting `TOP_TIER_ROLES` holder (excluding the target) at their `personal_email`. Call it **after** the commit — the recipient query reads live roles. It's a **detection** control, not prevention (see above); best-effort, returns a count, never raises, and a no-op PATCH (`old_role == new_role`) skips it so a re-save doesn't page the E-Board. Zero recipients is normal on the very first bootstrap promotion and must not error.
- Tests: `tests/admin_tests/test_bootstrap.py` (19). They call `bootstrap_structure`/`promote` directly with the `session` fixture rather than going through `main()`, which would open its own `Session(engine)` against the real dev database.

## President role & chapter admin
- **`Role.president` is the site-wide admin** — it was already in the Role enum; what's wired to it: membership in `SHOP_ADMIN_ROLES` (full shop manager), a bypass in `require_chair` + message access (every committee's chair tools), and the `/admin/*` endpoints (`routes/admin_routes.py`).
- **Role assignment is a two-tier privilege, not president-only.** `ROLE_ADMIN_ROLES = {president, vpe, vpi}` (`models/user/user_enums.py`, next to `SHOP_ADMIN_ROLES`) gates all `/admin/*` endpoints via `require_role_admin` in `services/dependencies.py` (mirrors `require_shop_admin`; it replaced the old `require_president`, which no longer exists). The **VP-specific limits are per-request, not in the gate** — `_assert_may_assign` in `admin_routes.py` 403s a non-president who tries to (a) assign a `TOP_TIER_ROLES` role or (b) modify a target who currently holds one. `TOP_TIER_ROLES = {president} | VP_ROLES`, so a VP can neither grant nor strip the presidency *or* either VP seat. Both halves are needed and for the same reason: without (b) a VP could demote the president or their peer; without (a) they could mint an ally into a peer seat, which is the same power one step removed. `GET /admin/roles` filters the whole top tier out of a VP's list so the dropdown can't offer a pick the PATCH would reject — that's convenience; `_assert_may_assign` is the enforcement, keep both.
- **Org tiers live in `user_enums.py`**: `VP_ROLES` (2), `TOP_TIER_ROLES` (3), `OFFICER_ROLES` (6), `EBOARD_ROLES` (9 — matches the About page's E-Board), `CHAIR_ROLES` (14). They're **listed explicitly, not derived from the display string**: `value.endswith("Chair")` selects exactly the 14 chairs today, but would silently absorb a future role like "Vice Chair". Mirrored as display-value strings in `utils/shop.js` (`isEboardRole`, `isChairRole`) — those match API payloads only, never raw DB rows, which store the enum *name*.
- **Nobody can change their own role** (400) — the check compares against the *acting* user, so it covers VPs as well as the president.
- **`/committees` reports `is_chair: true` on every committee for the president** (computed in the route, no membership rows involved) so the frontend Committees page shows the Manage panel everywhere. The president usually has `is_member: false` — the card then also shows a Join button; that's expected.
- **Role assignment must keep chair rows in sync**: chair permissions need BOTH `user.role == committee.chair_role` AND an `is_chair` membership row. `_sync_chair_memberships` in `admin_routes.py` handles both directions — assigning a chair role creates/reactivates the `is_chair` membership; removing one clears `is_chair` but keeps them as a regular member. Don't add another role-mutation path without it. (`bootstrap.py`'s `promote()` is the only other caller, and it imports this function rather than reimplementing it — see "Production bootstrap".)
- **There are exactly two role-mutation paths: `PATCH /admin/members/{id}/role` and `bootstrap.py`.** Both call `_sync_chair_memberships` and both call `notify_role_change`. Any third path must do the same, or a chair silently lacks permissions and a privilege change happens with nobody told.
- Handoff = the sitting president promotes the successor to President first (two presidents can coexist briefly), then the successor demotes them. A VP cannot perform either half.

## Reporting structure (org chart)
- **It grants no permissions. This is the single most important thing about it.** `models/role_report.py` + `services/structure_services.py` record who oversees whom for display; no permission check anywhere consults them. An officer with ten chairs under them has exactly the privileges their `Role` grants — role assignment stays gated by `require_role_admin` + `_assert_may_assign`. `test_supervising_grants_no_permissions` in `tests/admin_tests/test_structure.py` pins this down; if it ever fails, the tree has quietly become an authorization system.
- **Role→role, not person→person.** `RoleReport(role PK, supervisor_role)` — one row per managed role, so "one supervisor per role" holds by construction and a re-parent is an upsert. Keyed this way the tree survives elections and chair handovers untouched, the same reasoning behind `Committee.chair_role` mapping a role (not a user) onto a committee. Co-chairs share a role and therefore share a supervisor.
- **Tier rules** (`structure_services.valid_supervisors`): officers report to a VP; chairs report to a VP or an officer; the president is the root and VPs always report to them, so **neither is stored** — `get_structure` synthesizes the VP→president link. Because every allowed edge points strictly upward a cycle is unreachable, so there is deliberately no cycle check to maintain. Violations are 400.
- The Structure tab renders a **real tree**, not an indented list: `StructurePanel` groups nodes into a `supervisor_role -> children` map and `OrgBranch` recurses from the president. Nesting is therefore **driven by the data, not by tier position** — a chair parked directly under a VP lands in the right place with no special case. Roles with no supervisor can't hang off the tree at all, so they're surfaced in a separate "Not in the chart yet" panel instead of silently vanishing. The elbow connectors are the `.orgTree` rules in `styles.css` (pseudo-elements can't be inline styles — the documented exception); everything else on the panel stays inline like the rest of the page.
- `GET /admin/structure` returns all 23 tree roles (president + 2 VPs + 6 officers + 14 chairs) in `Role` declaration order — which already reads president → VPs → officers → chairs, so the frontend needs no sort. Each node carries its `tier`, `supervisor_role` (**null = unassigned**, surfaced in the UI), and `holders` (empty = vacant). Two queries total.
- **Registered in `database.py` next to the other models**, which is what puts it in front of Alembic's autogenerate. (Historical note: this table predates Alembic and originally appeared on its own via `create_all()` at startup — a new table added today needs a migration.)
- `chapter_data.py`'s `DEFAULT_REPORTS` is the chapter's **real 2026-2027 org chart** (20 links covering all 6 officers and all 14 chairs): NMR/Treasurer/Regional Rep under VPE, Comms Director/Secretary/DIA under VPI, chairs beneath those. ## Event tracker sheet sync
- `services/event_tracker_services.py` pulls the chapter's event-tracker Google Sheet (gspread, **read-only** `spreadsheets.readonly` scope, service-account creds via `CREDENTIALS` + `SHEET_ID`) and reconciles it into the `Event` table. `main.py` runs `sync_events` in a background asyncio loop that fires **daily at 6 AM Central** (`SYNC_HOUR` + `seconds_until_next_sync`, started in `lifespan`). Unconfigured = dev-mode no-op: `fetch_sheet_events()` prints and returns `[]`.
- **Identity is `Event.source_row_id` = `event_key(date, title)` → `"2026-08-05|gbm 1"`** (ISO date + lowercased, whitespace-collapsed name). This is the *join* between a sheet row and a DB row — the auto-increment `Event.id` can't serve that role because the sheet has no column holding it, so without the key every sync would re-insert everything. The column is `index=True, unique=True`; **NULLs stay exempt** (SQL unique indexes treat NULLs as distinct), which is what lets `seed.py` and hand-added events coexist.
- **There is deliberately NO delete/sweep pass** — rows are only created or updated. All of the following are accepted tradeoffs, not bugs:
  - **Rescheduling adds a row instead of moving one.** A new date means a new key, so the old row stays behind and the calendar shows both. Chosen over a sweep because delete+reinsert mints a new `Event.id`, which silently orphans `EventReminder` **and `EventHost`** rows (the join in `send_due_reminders` simply stops matching — no email, no error, and the calendar button resets as if the member never set it) and resets `points_value`, which doesn't exist in the sheet (`event_type` would actually come back correctly, since it's sheet-derived now — the `Event.id` churn is the disqualifying problem regardless). A visible duplicate someone fixes by hand beat a silent failure.
  - **Renames behave the same way** — the name is half the key.
  - **Deleting a sheet row does not remove the event.** The chapter confirmed nobody deletes rows.
  - If a sweep is ever added, it MUST scope to `source_row_id IS NOT NULL`, bail out when the fetch returns zero rows (an unconfigured or failed fetch returns `[]`, which would otherwise wipe the entire calendar), and decide what happens to existing reminders.
- `EXCLUDED_EVENTS` (normalized names — currently `"c&e retreat"`, `"national convention"`, `"thanksgiving break"`) are dropped in `parse_row` before the date is even parsed. **One-way door:** because nothing deletes, an event already synced before its name was added to the set stays in the DB forever.
- Row handling: the header row and the row-2 template row are skipped (`get_all_records()[1:]`), and a per-row `try/except` isolates failures so one unparseable date doesn't kill the batch. Note `parse_row` reads DATE with direct indexing (`row[COLUMNS["date"]]`), so renaming that sheet header would make **every** row raise, get swallowed, and log a cheerful "0 created, 0 updated" while doing nothing.
- Times: `parse_time` returns None for blank / `All Day` / `TBD`, so those events fall back to **local midnight**. `end_time` is built from the same `day` as the start — an event crossing midnight would store an end *before* its start. Confirmed no chapter events run past midnight; revisit if that changes.
- `parse_date` stamps the **current Central year** onto the sheet's MM/DD values. This is correct in normal use because the trackers are **semester-scoped** — the fall sheet runs Aug–Dec and spring is a separate sheet (Jan–May), so every row in one pull shares a calendar year. Do NOT "fix" this by adding a year column; it isn't needed.
- **The one hazard is `SHEET_ID` still pointing at the fall sheet on January 1.** The 6 AM sync then re-reads `09/15` as September of the *new* year, minting a new key for every row and inserting the entire fall semester as ghost events dated a year out — which persist, since nothing deletes. Either swap `SHEET_ID` to the spring sheet before January, or make `parse_date` anchor to the academic year (`now.year` if `now.month >= 8` else `now.year - 1`; months 8–12 take the anchor, 1–7 take anchor + 1), which keeps `09/15` at 2026 even when read in January 2027.
- Duplicate keys inside one pull collapse to one row: the first row is `session.add()`-ed but still pending, and the second row's existing-lookup SELECT triggers SQLAlchemy's autoflush, which writes the first INSERT before the query runs — so the second row finds it and updates in place. Result is `(created, updated) == (1, 1)` and one row holding the *second* row's values, no `IntegrityError`.
- **Credentials live in `backend/secrets/`** (gitignored via `backend/.gitignore`, alongside `.env`), and `CREDENTIALS` is conventionally the relative path `secrets/<file>.json`. `Credentials.from_service_account_file` resolves that against the **process CWD**, so it only works when the backend is started from `backend/` — which is how the project is run and how the tests run. An absolute path is the fix if that ever changes; a wrong CWD surfaces as `FileNotFoundError` swallowed by `event_sync_loop`'s `except`, i.e. a calendar that silently never populates.
- **`event_type` and `EventHost` are populated by every sync**, via `resolve_committee`/`get_event_type` in `services/event_tracker_services.py` (reading the `OWNER(S)` and `COLLAB(S)?` columns). Two lookup tables, both keyed on the **sheet's own spelling** (lowercased, whitespace-collapsed) rather than `Committee.name`, because they differ (`"wellness & athletics"`, `"project"`, `"shpe jr."`, `"eec"`, `"cfc"` vs the DB names in `seed.py`): `COMMITTEE_ROLES` (16 keys → the 14 chair `Role`s) and `EBOARD` (10 sheet abbreviations for E-Board positions — `"vpe"`, `"communications"`, etc, **not** `Role` display values). `EBOARD` is a **dict, not a set** (it was a set until E-Board got `Committee` rows): each specific position maps to its `Role` so `EventHost` rows get written, and the bare `"eboard"` catch-all maps to **`None`**, which is a *real* match — the generic "E-Board" committee has `chair_role=None`. That's why `resolve_committee` returns a **`NO_MATCH` sentinel** instead of `None` for "not recognized at all": once `None` became a legitimate resolution it could no longer double as the miss signal, and `parse_row` filters `host_roles` on `is not NO_MATCH`. Using `None` for both would silently link every blank `OWNER(S)` cell and every outside-org collab (`"NSBE"`) to the generic E-Board committee. **The two dropdowns (OWNER(S) vs COLLAB(S)?) disagree on spelling** for two of the fourteen committees, so `"project"`/`"projects"` and `"shpe jr."`/`"shpe jr"` each get their own `COMMITTEE_ROLES` key mapping to the same `Role` — two divergences in fourteen committees is a high enough rate that it's worth re-checking both option lists by hand if a 15th committee is ever added. `_normalize_owner` strips a trailing `"- <chair name(s)>"` and `"Chair"/"Chairs"` so one function reads both columns: OWNER(S) has both to strip, COLLAB(S)? has neither so both strips are no-ops and a bare value falls straight through. **Logging is deliberately asymmetric**: `resolve_committee` (COLLAB(S)?) stays silent on a miss — an outside org (`"NSBE"`) is the normal case, not an anomaly; `get_event_type` (OWNER(S)) warns on a miss and still files the event under `"eboard"` rather than `None`, so a genuinely unrecognized value (a new dropdown option, a typo) stays reachable by whoever's most likely to notice it, instead of vanishing from every tab with `event_type = None`.
- **`sync_events` reconciles `EventHost` rows** from the parsed `host_roles` list (owner role + collab role, resolved via the same lookup, `None`s dropped in `parse_row`). `host_roles` is popped off the parsed dict as the first statement inside the loop — it isn't an `Event` column, and unlike `Event(**data)` (which silently drops an unrecognized constructor kwarg), `setattr` on an already-built SQLModel instance raises `ValueError` on one, so it must come out before the create branch *and* the update branch. A `Role -> Committee.id` map is built once per sync, not per row, and a newly-created `Event` needs `session.flush()` before its `.id` exists for the host lookup. **Reconciliation deletes stale host rows** (the `existing - wanted` set difference) — a deliberate, narrow exception to this file's no-delete rule above: unlike `Event`, `EventHost` has no dependents, so dropping a row no longer in the sheet is safe, and leaving hosts additive-only would let a chair keep seeing — and minting QR codes for — an event they were dropped from as a collab. The mirror-image `wanted - existing` add-only-what's-missing is what keeps a second sync from raising `IntegrityError` on the composite PK instead of just leaving the row alone. A role with no matching `Committee` row logs a warning and is skipped rather than failing the sync.
- **The QR attendance backend is built** (see "QR attendance & points" below). `EventHost` is what scopes a chair to an event, so the host reconciliation above is load-bearing for permissions, not just display.
- Tests live in `tests/event_tracker_tests/` (`test_event_parsing.py`, `test_event_sync.py`) and use two deliberate seams: `fetch_sheet_events` tests monkeypatch `get_worksheet` with a fake worksheet so the real parse path runs, while `sync_events` tests monkeypatch `fetch_sheet_events` directly so they only exercise DB reconciliation. An autouse `disable_event_tracker_sync` fixture in `tests/conftest.py` clears `CREDENTIALS`/`SHEET_ID` — same `load_dotenv()` leak problem as the Drive and Square fixtures.

## QR attendance & points
- **Members earn points by scanning a QR at an event.** The QR encodes a **URL to our own site** (`/attend/<code>`), so the member's **native phone camera** opens it — there is deliberately **no in-app scanner**, no camera permission, and no QR-decoding dependency. The code in the QR is the same secret either way, so a scanner would add cost and buy nothing.
- **Each event has two codes** (`Event.sign_in_code` / `sign_out_code`, both `index=True, unique=True`), plain random strings from `secrets.token_urlsafe(16)` — a QR is a rendering of a string, nothing binary is stored. Minted lazily by `ensure_event_codes()` the first time a chair views the event (idempotent), **not** at sync time.
- **`resolve_code()` is why there's one endpoint and one page for both QRs.** Both codes live on the same row in different columns, so the scanned string alone doesn't say which it is; it looks up `sign_in_code`, then `sign_out_code`, and returns `(event, "in" | "out")`. Because the action rides on *which code was scanned*, a mislabeled QR is impossible — don't "simplify" this into two endpoints that take the action as a parameter.
- **Points come from the rule alone — `default_points()` — and nothing is stored on `Event`.** Regular event `(2, 2)`, GBM `(3, 2)`. There are deliberately **no per-event overrides**: chairs cannot edit point values. `Event.points_value` is now **computed on read** by `_event_out()` in `event_routes.py` (the raw column stays 0), which is what feeds the `+N pts` badge at `pages/dashboard.jsx:106`.
- **GBM detection is `event_type == "eboard"` AND `"GM" in title`, and the case-sensitivity is load-bearing.** A `.lower()` match would also hit ordinary words containing "gm" (e.g. "Segment"). Both halves are needed: `eboard` alone would promote "Cat's Back Day", and the title alone would promote "SHPE JR 1ST GM" (a committee's GM, `event_type = shpe_jr`). Verified against the live sheet data — the conjunction selects exactly the 5 real GBMs.
- **Codes expire when the event ends — that is the whole replacement for revocation.** There is no regenerate/revoke endpoint and no need for one. `is_expired()` uses `event.end_time or _end_of_local_day(event.start_time)`, and **the Central-day fallback is load-bearing**: many events have no `end_time`, and blank / `All Day` / `TBD` sheet times already fell back to local midnight, so keying expiry on UTC midnight would expire those events *before they started*.
- **A code also doesn't work more than 60 minutes before `start_time`** (`attendance_services.is_not_started`, `NOT_STARTED_GRACE_MINUTES`) — `POST /events/attend` 425s a scan that arrives earlier than that. The grace window (not a hard `now < start_time`) is deliberate and asymmetric with `is_expired`'s end-of-local-day fallback for the same underlying reason: many events' `start_time` is a sheet-sync midnight fallback rather than the real door time, so a hard check would reject nobody there (midnight is early, not late) while rejecting a member who shows up 10 minutes early to a real timed event. The frontend normally never triggers the 425 — `GET /events/code/{code}` (the mobile flow's preview call) reports `state: "not_started"` first and the page renders the "Check-in hasn't opened yet" screen without ever POSTing; the 425 is the backstop against a direct POST.
- **Never double-award — `User.points` is a running total.** A repeat sign-in returns **200 "already signed in"** with `points_awarded: 0` (a double-scan must not look like a failure), not an error. `record_sign_in` guards with a `session.get()` check **and** catches `IntegrityError` for two simultaneous scans racing past it. `EventAttendance`'s composite PK `(user_id, event_id)` is what makes the new-member bonus structurally once-per-event.
- **"Did you bring a new member?" is +2** (`NEW_MEMBER_BONUS`), asked **only on the sign-in scan**, and captures `new_member_name`. Honor-system: the name makes it auditable, not enforced.
- **The "Assist" point values on `pages/membershpe.jsx` (Outreach +4, Professional +3, …) are a SEPARATE process** — they're for *helping run* an event, not attendance. Do not fold them into `default_points()`.
- **Two-layer access control, and both layers are needed.** `require_event_host` (in `dependencies.py`, mirrors `require_shop_admin`) is a coarse role gate — any chair or E-Board member. The per-event scoping lives in `attendance_services.host_scoped_events()` and goes **through `EventHost`**; an unscoped `is_chair` check would hand every chair every event's codes. Same relationship `require_chair` has to committee-specific checks. The president's full-access bypass lives in `host_scoped_events`, not the gate (they already pass it, since `TOP_TIER_ROLES ⊆ EBOARD_ROLES`).
- **E-Board members see every E-Board event**, resolved as `Committee.joinable == False` rather than by re-deriving from `EBOARD_ROLES` (which would miss the generic row, whose `chair_role` is `None`). Officers run GBMs collectively, and keying on the **live** `user.role` means access self-corrects after an election instead of drifting with stale membership rows.
- **`Committee.joinable`** (default True) is False for the 10 E-Board rows `chapter_data.py`'s `EBOARD_COMMITTEES` defines (created by `seed.py` locally, `bootstrap.py` in production) — 9 keyed to a position's `Role` plus one generic `"E-Board"` (`chair_role=None`) for the sheet's bare `"eboard"` value. They exist **only** so `EventHost` has something to point at; they are not committees members can join, and `get_all_committees()` filters them out so `/committees` is unchanged. `_sync_chair_memberships` needed **no change** — it already keys purely off `Committee.chair_role` with no `CHAIR_ROLES` restriction, so assigning someone VPE creates their `is_chair` row automatically.
- **The flag is enforced on two write/read paths as well as the listing filter, and where those checks live is deliberate.** `join_committee` 404s a `joinable=False` committee, and `GET /committees/{id}/messages` requires a non-chair's committee to be joinable *in addition to* an active membership. ## Signup form (`pages/signup.jsx`)
- **Five steps in ONE `<form>`.** Only the last step's button is `type="submit"`; the rest are `type="button"` calling `nextStep()`. That means pressing **Enter** in any text field on steps 1-4 fires the form's submit handler — which used to POST a half-filled payload and surface the API's 422 as unexplained errors (this is why "country of origin is empty" only appeared at the very end). `handleSubmit` now starts with `if (step < STEPS.length - 1) { nextStep(); return; }`, so Enter behaves as Next. **Keep that guard** if you touch the submit path.
- **`touched` is keyed by STEP, not by field** — `{ 2: { psid: true } }`, and `err(field)` reads `touched[step]?.[field]`. This shape is deliberate. A flat `{ psid: true }` map meant every transition had to remember to clear it, and any path that didn't left a fresh step opening covered in "required" errors before the member typed anything (this shipped, and the flat map made it impossible to pin down which writer was at fault — `onBlur`, browser autofill, and the Next handler are all candidates). Keyed by step there is nothing to reset: a step the member hasn't interacted with simply has no entry. **Don't flatten it back.**
- **`validateStepAt(index)` takes the step explicitly** so the final submit can re-check every earlier step (`firstIncompleteStep()`); on failure it jumps back to the offending step and calls `touchAllOnStep(incomplete)`. `validateStep()` is just `validateStepAt(step)`.
- **`FIELDS_BY_STEP` drives which fields `touchAllOnStep` marks.** Adding a validated field means adding it there too, or its inline error never appears.
- `goToStep()` is the only thing that changes step; it clears `submitError` (which is about the step you were on) and no longer touches `touched`. Don't call `setStep` directly.
- **Client rules mirror the backend on purpose** — `NAME_RE` matches `_SAFE_NAME_RE` in `user_schemas.py`, and the password minimum matches `MIN_PASSWORD_LENGTH`. Diverging means the form accepts something the API then rejects after five steps of typing.
- **Phone is US-only, exactly 10 digits.** `formatPhone` rewrites input to `(555) 555-5555` and hard-caps at 10 digits; `validate_phone` in `user_schemas.py` enforces the count server-side (stripping a leading `1` country code). The regex alone accepts 7-20 characters, so the digit count is the real rule.
- **`country_origin` is required and multi-select** — a `<select>` of `constants/countries.js` plus an Add button, rendering chips. It is validated in step 4 (`Background`) like the other multi-selects. The backend requires ≥1 (`UserCreate`), which is what made it a late 422 before.

## Email verification at signup
- `models/user/email_verification.py` — `EmailVerificationToken(user_id, token_hash, created_at, expires_at, used_at)`, same shape as `PasswordResetToken`. **Reuses** `generate_reset_token()`/`hash_reset_token()` (only the SHA-256 hash is stored). Active while `used_at` is NULL and not expired; TTL is 24h. Registered in `database.py` (imported next to `pw_reset_token`).
- `User.email_verified: bool` (on the **User table model**, defaults False). `authenticate_user` stays pure (`User | None`); the verified check lives in the `/login` route (403 "verify your email"). A new column on an existing table needs the in-place ALTER (`... ADD COLUMN email_verified BOOLEAN DEFAULT 0;`) then backfill existing members to 1 — or just reseed.
- **Signup flow** (`routes/auth_routes.py`): `/signup` creates the user unverified, mints a token, emails `{FRONTEND_URL}/verify-email?token=<raw>` to cougarnet_email, and returns a **generic message (no JWT)**. Rate limited by `RATE_LIMIT_SIGNUP` (default 60/hour). **Squat reclaim:** an existing *unverified* account for the same email is deleted (via `_delete_unverified_user`, which also clears the four multi-select child rows + verification/reset tokens — the DB doesn't cascade-delete those child rows on its own, so they'd otherwise be left as orphans) and re-created; only a *verified* email 409s. Re-submitting signup for an unverified email therefore doubles as "resend link". (Postgres sequences never reuse a deleted row's id — unlike SQLite, a later user can't silently inherit the reclaimed id — but the child-row cleanup is still required regardless, since nothing cascades.)
- **`UserBase.psid` is `unique=True`** (`user_schemas.py`, alongside the existing `cougarnet_email`/`personal_email` uniqueness) — a PSID is UH's PeopleSoft ID, a real-world identifier, so it must map to at most one account. `services/user_services.py`'s `get_user_by_psid()` mirrors `get_user_by_email()`. The signup route runs the **same squat-reclaim logic a second time, keyed on PSID, checked SECOND (after email)** — a duplicate PSID against a verified account 409s ("That PSID is already registered.", distinct wording from the email 409 so the frontend message is unambiguous); against an unverified account it deletes the pending row via `_delete_unverified_user` (same child-row cleanup) and proceeds. **Order is load-bearing**: in the common case (the same person re-submitting signup unchanged) one pending row holds both the email and the PSID, so the email branch deletes it first and the PSID branch is a no-op against an already-gone row — checking PSID first would work too for that case, but the comment in `auth_routes.py` documents email-first as the chosen order. If the two lookups instead resolve to two *different* unverified rows, both get deleted, which is correct (both are dead pending rows). `AdminMemberOut.psid` (the admin member-directory schema) is a separate, non-unique field and was deliberately left untouched.
- **Confirm** (`/verify-email`, `EmailVerifyConfirm{token}`): looks up by hash, rejects unknown/used/expired **and orphaned** (user deleted by a later reclaim) tokens with a generic 400, else stamps `email_verified=True` + `used_at` and returns a login JWT. Idempotency: the frontend verify page guards the single-use POST with a `useRef` so React StrictMode's double-invoke doesn't 400 the second call.
- **Seed** sets `email_verified=True` on all seeded accounts (test users, chairs, comms director, president) — otherwise none could log in after a reseed. `tests/conftest.py`'s `make_user` also defaults `email_verified=True` (fixture users are established members); tests for the flow itself live in `tests/auth_tests/test_email_verification.py`.
- **Frontend:** `pages/verify-email.jsx` at route `/verify-email` (in `App.jsx`); signup shows a "check your email" screen instead of logging in; signin maps 403 to a "verify your email" message. `api.js`: `verifyEmail(token)` (public).

## Password reset & rate limiting
- `models/user/pw_reset_token.py` — `PasswordResetToken(user_id, token_hash, created_at, expires_at, used_at)`. Only the **SHA-256 hash** of the raw token is stored (the raw token is high-entropy `secrets.token_urlsafe(32)`, so SHA-256 — not Argon2 — is correct here). A token is active while `used_at` is NULL and `expires_at` is in the future; TTL is 1 hour. Requesting a new reset retires any prior active tokens for that user.
- `services/pw_reset_services.py` — `generate_reset_token()` / `hash_reset_token()`.
- `routes/pw_reset_routes.py` — `POST /password-reset/request` and `POST /password-reset/confirm`. **Never reveal whether an email exists**: request always returns the same 200 body (even if `send_email` fails), and confirm returns one generic 400 for unknown/used/expired tokens. Reset emails go to **cougarnet_email** (the verified UH address). The link is `{FRONTEND_URL}/reset-password?token=<raw>`.
- Confirm reuses the shared `validate_password_strength()` from `models/user/user_schemas.py` (also used by `UserCreate`) — change password rules there, in one place.
- **Password policy (NIST 800-63B style):** min 10 chars (`MIN_PASSWORD_LENGTH`), max 128 (`MAX_PASSWORD_LENGTH`) in `validate_password_strength` (`models/user/user_schemas.py`) — deliberately NO composition rules (upper/digit/special) and NO expiry; both are counterproductive per NIST. The schema validator is **pure/sync only** (pydantic runs it during request parsing) — don't put network calls in it. The breached-password check lives in the routes instead: `services/hibp_services.py` `is_password_pwned()` queries the Have I Been Pwned range API (k-anonymity — only the first 5 SHA-1 hex chars leave the server; **fail-open**: any error logs and allows). `/signup` and `/password-reset/confirm` call it via `await asyncio.to_thread(hibp_services.is_password_pwned, ...)` — as a **module attribute** so tests can monkeypatch — and reject with **422** (not 400 — the reset page shows "invalid link" for 400) *before* any DB mutation / before marking the reset token used. Tests never hit the network: an autouse `disable_hibp_check` fixture in `tests/conftest.py` stubs it to False. Side effect: `seed.py` calls `create_user()` directly (never the routes), so the seed password `password123` seeds fine. The frontend length checks in `signup.jsx` and `reset-password.jsx` mirror the minimum — keep them in sync.
- **Login lockout (per-account):** 10 consecutive failures (`LOCKOUT_THRESHOLD` in `routes/auth_routes.py`) lock the account for 10 minutes (`LOCKOUT_MINUTES`) → **429 "Too many attempts. Try again later."** raised *before* the Argon2 verify (cheap reject; signin.jsx already maps 429 to a "too many attempts" message). Every failure for an existing email increments `User.failed_login_count` and **commits**; an expired lock is cleared (both fields) before the attempt is evaluated; a successful login resets both fields. Wrong credentials stay a generic 401. The two columns (`failed_login_count`, `locked_until`) live on the `User` table model. Complements (does not replace) slowapi's per-IP limit on `/login` — in lockout tests, call `limiter.reset()` between attempts or the IP limit's 429s shadow the lockout's.
- **JWT invalidation:** `create_access_token` sets `iat`; a successful reset stamps `User.password_changed_at`, and `get_current_user` rejects tokens whose `iat` predates it. PyJWT floors `iat` to whole seconds while `password_changed_at` keeps microseconds, so the comparison is at **whole-second granularity with strict `<`** — a token issued in the same second as the reset stays valid. Tokens without `iat` are rejected once `password_changed_at` is set.
- **Rate limiting (slowapi):** the `Limiter` lives in `services/rate_limit.py` (NOT `main.py` — route modules import it, and importing from `main` would be circular). `main.py` attaches it to `app.state` and registers the 429 handler. The limits are **named constants in `rate_limit.py`, each overridable by env var** — `LOGIN_LIMIT` (`RATE_LIMIT_LOGIN`, 60/minute), `SIGNUP_LIMIT` (60/hour), `ORDER_LIMIT` (60/minute), `PASSWORD_RESET_LIMIT` (20/hour), `ATTEND_LIMIT`/`CODE_PREVIEW_LIMIT` (600/minute), `UPLOAD_LIMIT` (`RATE_LIMIT_UPLOAD`, 60/minute, on both upload routes) — so a limit can be retuned for an event without a code change. Routes reference the constants, never a literal. The key function is `client_ip`, **not** slowapi's `get_remote_address` (see "What NOT to do"). slowapi-decorated endpoints must take a `request: Request` parameter, with the `@limiter.limit(...)` decorator **below** the router decorator.
- **`JOIN_LIMIT` is the one budget keyed on the ACCOUNT rather than the IP** (`RATE_LIMIT_COMMITTEE_JOIN`, 30/hour, spent by `POST /committees/{id}/join`). It uses the same manual `limiter.limiter.test()`/`.hit()` primitive as `FAILED_CHARGE_LIMIT` — `join_budget_exhausted(user_id)` checks, `record_join(user_id)` spends — but passes `str(user.id)` as the identifier instead of `client_ip(request)`, so the handler needs no `request: Request` parameter at all. Per-account is the point, not an accident: the NAT sizing that every other limit here is built around is exactly what makes a per-IP join limit useless. A limit loose enough not to starve an involvement fair (a room of members on one campus IP, each joining several committees) is far too loose to constrain one member looping the endpoint, and the route is authenticated so the right bucket is already in hand. 30/hour because 14 committees is the ceiling on distinct legitimate joins, leaving headroom for real churn. When adding another per-account budget, copy this shape rather than reaching for a decorator — `@limiter.limit` keys on the IP via the limiter's `key_func` and there is no way to override it per-route.
- **`/login`'s per-IP limit bites manual curl verification.** A script that mints a token per check can burn the budget; login then returns 429, the usual `.get("access_token", "")` yields an empty string, and every following request 401s with "Could not validate credentials" — which reads as wrong credentials, not rate limiting. Mint one token and reuse it across checks, or retry the login until it succeeds.
- slowapi's counters are in-memory and persist across tests in one process — `tests/conftest.py` has an autouse `reset_rate_limiter` fixture calling `limiter.reset()` so counts don't bleed between tests. Auth tests that must exercise real JWT flow use the `unauth_client` fixture (`client` overrides `get_current_user` and bypasses auth).
- The `password_changed_at` column lives on the `User` TABLE model (not `UserBase`), same pattern as `resume_filename`. Adding it required a full db rebuild at the time (done, pre-Alembic); the same change today is an `alembic revision --autogenerate` plus `alembic upgrade head`.
- Frontend: `/forgot-password` (always shows the same "check your email" confirmation) and `/reset-password` (reads `?token=`, new + confirm fields, redirects to `/signin` with `location.state.message` on success — signin renders that message). Sign-in has a "Forgot password?" link and maps 429 to a "too many attempts" error. `api.js`: `requestPasswordReset`, `confirmPasswordReset` — both **public**, no auth headers.

## Profile page & resume uploads
- `pages/profile.jsx` (route `/profile`, in the member dropdown under Committees) shows the signed-in user's info **read-only** (no editing) plus a resume section. It reads everything from `useAuth().user` (the `/me` payload) and tracks resume state locally.
- Resumes are **PDF only** and **private to the owner** (no chair/other-user access). `User.resume_filename` (nullable, on the `User` table model — NOT `UserBase`, so signup is untouched) stores the canonical `First_Last_PSID.pdf` name; `UserOut` exposes it so the frontend knows whether a resume exists. The PDF lives on disk at `backend/uploads/resumes/user_<id>.pdf` (deterministic → re-upload overwrites).
- `routes/resume_routes.py` validates uploads (PDF content-type + `.pdf` ext + `%PDF` magic bytes, ≤2 MB) and serves the file via `FileResponse`. Storage dir is `RESUME_DIR` (a module constant) — tests monkeypatch it to a `tmp_path` to stay hermetic. Every resume is **renamed to `First_Last_PSID.pdf`** (`_canonical_resume_name()` — multi-word names join with underscores, uploaded filename discarded); that canonical name is used for `resume_filename`, the download name, and the Drive copy. The profile page also pre-checks type and the 2 MB cap client-side for instant feedback — keep the two limits in sync.
- **Google Drive sync** (`services/drive_services.py`): when `GDRIVE_RESUME_FOLDER_ID` + credentials are set, uploads mirror the PDF to that Drive folder under the same canonical `First_Last_PSID.pdf` name and deletes remove it. `User.resume_drive_file_id` (table model, internal — NOT in `UserOut`) tracks the Drive file: re-uploads **update in place** (same file id → no orphans; 404 falls back to create), and a failed Drive delete keeps the id so the next upload replaces the orphan. Sync is **best-effort**: failures are logged, never raised — the local file in `uploads/resumes/` stays the source of truth, and without config uploads are a console-printing no-op (same dev-mode pattern as `email_services.py`).
- **`delete_resume_from_drive` is the one Drive call whose unconfigured path returns FAILURE, and that asymmetry is deliberate** — see the "What NOT to do" entry. Its contract is three-way: `True` = the Drive copy is gone (nothing to delete / deleted / already 404); `False` = it may still be there (Drive unreachable **or unconfigured**), so the caller keeps `resume_drive_file_id`. `drive_services.is_configured()` (mirrors `square_services.is_configured()`, presence-only, read at call time) is the shared four-var check used by both `_drive_config()` and `assert_production_config()`. The googleapiclient is blocking → routes call it via `asyncio.to_thread`. Deps: `google-api-python-client`, `google-auth`, `google-auth-oauthlib` (helper script only). Drive tests monkeypatch the two functions on `routes.resume_routes` (they're imported there by name); an **autouse `disable_drive_sync` fixture in conftest.py clears all `GDRIVE_*` env vars** so tests never hit the real API even when `backend/.env` has live credentials (drive config is read at call time, and `load_dotenv()` leaks .env into the test process).
- **Credentials — OAuth only, deliberately.** The backend uploads *as the folder owner's Google account* via `GDRIVE_OAUTH_CLIENT_ID`/`_SECRET`/`_REFRESH_TOKEN`. There is intentionally **no service-account path**: Google 403s service-account uploads to personal My Drive folders (`storageQuotaExceeded`: "Service Accounts do not have storage quota — use shared drives or OAuth delegation"); SA keys only work with Workspace Shared Drives, which the chapter doesn't have — don't re-add one. Mint the refresh token once with `backend/get_drive_refresh_token.py <client_id> <client_secret> [folder name]` (Desktop-app OAuth client; consent screen must be **In production** or refresh tokens die after 7 days). Setup steps live in the README.
- **OAuth is scoped to `drive.file` — one folder only, by design.** The token can only see files/folders the app itself created, never the rest of the owner's Drive. Consequence: `GDRIVE_RESUME_FOLDER_ID` **must** be the app-created folder id printed by `get_drive_refresh_token.py` (the script creates or reuses a folder, default name "SHPE Resume Book") — pointing it at a hand-made folder 404s. The owner can move/rename the folder in Drive freely (sync is id-based), but renaming means a script re-run would create a fresh folder instead of reusing it. Don't "fix" upload 404s by widening the scope to full `drive` — that's the privacy boundary the owner asked for.
- Frontend: viewing fetches the PDF as a **blob** (`getResumeBlob`, `responseType: "blob"`) and opens it with `URL.createObjectURL` — a bearer token can't ride on an `<iframe>`/`<a href>`. `api.js` functions: `uploadResume` (don't set `Content-Type` — let axios add the multipart boundary), `getResumeBlob`, `deleteResume`.
- **Schema changes go through Alembic** (`backend/alembic/`, config in `backend/alembic.ini`, baseline revision `b11fde67a1dd`). A new/changed column on an existing model is picked up with `alembic revision --autogenerate -m "<what changed>"` run **from `backend/`** (`prepend_sys_path = .` puts the CWD on `sys.path`, which is the only reason `from database import ...` resolves inside `env.py`), then **read the generated file** before `alembic upgrade head` — autogenerate is a first draft, not an oracle. Three things make this work and each is easy to break:
  - **`alembic.ini`'s `sqlalchemy.url` is deliberately blank**, and `env.py` builds its own `create_engine(DATABASE_URL, poolclass=NullPool)` rather than using `engine_from_config` — which is what makes the blank value harmless instead of a crash. The URL comes from `database.DATABASE_URL`, so it resolves from `.env` / Railway exactly the way the app resolves it and no DB password is ever committed. It also sidesteps ConfigParser interpolation, which would require a `%` in a generated password to be doubled to `%%` in the ini.
  - **`env.py`'s `from database import DATABASE_URL` is load-bearing twice over.** Importing that module runs its body, which imports every model module and populates `SQLModel.metadata` — the registry `target_metadata` points at. Without it, autogenerate either fails with "environment script ... does not provide a MetaData object" or (worse) emits an empty migration.
  - **`alembic/script.py.mako` carries an added `import sqlmodel`.** Autogenerated revisions render SQLModel string columns as `sqlmodel.sql.sqltypes.AutoString()`, which the stock template never imports — revisions then generate fine and die with `NameError` at upgrade time.
- **A named enum reused across tables is fine, despite appearances.** The baseline declares `sa.Enum(..., name='role')` four times (`committee.chair_role`, `rolereport.role`/`supervisor_role`, `user.role`), which looks like it must fail with `type "role" already exists`. It doesn't: Alembic's `DefaultImpl` keeps a `memo` dict for the whole migration run (`alembic/ddl/impl.py`) and passes itself as `_ddl_runner`, so SQLAlchemy's `_check_for_name_in_memos` emits `CREATE TYPE` once and skips the rest. Don't "fix" this by hand-editing the duplicates out.
- **`create_db()` no longer creates tables** — it only makes the upload dirs. Alembic owns the schema, so a `create_all()` there would be a second, competing authority: on a fresh database whichever ran first would win, and an app boot that beat the migration would leave Alembic trying to create tables that already exist. `tests/conftest.py` still calls `SQLModel.metadata.create_all()` directly and **should keep doing so** — the suite builds its schema in one shot, which is faster and independent of migration history.
- **Wipe-and-reseed is still the fastest local reset, but it is no longer how a schema change is applied**: `docker compose down -v` (the `-v` is essential — a plain `down` keeps `pgdata` and the stale schema survives) → `docker compose up -d --wait` → `docker compose exec db createdb -U shpe shpe_test` → `cd backend && alembic upgrade head && python seed.py`. The `--wait` matters: without it `createdb` races the container's first-boot `initdb` and fails with `connection to server on socket ... No such file or directory`, which reads like a broken config rather than a two-second timing problem.
- **Native enum types survive a bare `DELETE FROM`.** SQLModel maps Python enums (`Role`, `Classification`, …) to real Postgres `CREATE TYPE ... AS ENUM` types, not a plain text/check-constraint column. Adding a new `Role` value in code and then only deleting rows (instead of wiping the volume) leaves the old `CREATE TYPE` in place with the old value set — the new value doesn't exist in the db until the type itself is recreated. This is the specific reason the reseed procedure above destroys the whole volume rather than truncating tables. **Alembic does not close this gap** — see the autogenerate entry in "What NOT to do".
- **Use `postgresql+psycopg://`, not a bare `postgresql://`.** SQLAlchemy 2.0's default dialect for a schemeless `postgresql://` URL is `psycopg2`, which this project does not install (it uses `psycopg` — psycopg 3). Leaving off the `+psycopg` suffix fails at engine-creation time with a driver-not-found error.
- **`pool_pre_ping=True` (in `database.py`) is required, not decorative.** Restarting the `db` container (or `docker compose down`/`up`) invalidates every connection already in SQLAlchemy's pool; without pre-ping the next request reuses a dead connection and fails instead of transparently reconnecting.
- **In CI, a service container's port mapping is `host:container`, and the container side is always `5432`** regardless of what host port is chosen — Postgres inside the container always listens on 5432. Mapping `5433:5433` (matching the host port on both sides) silently binds nothing on the container's actual listening port, and every test fails to connect. `.github/workflows/ci.yml`'s postgres service maps `5433:5432` for this reason.
- **Tests dropping and recreating the schema is exactly why `tests/conftest.py`'s `_test`-suffix guard on `TEST_DATABASE_URL` matters** — the `engine` fixture calls `drop_all()` before `create_all()`, so a misconfigured `TEST_DATABASE_URL` that accidentally points at the dev `shpe` database would wipe it. The guard (`pytest.exit` unless the db name ends in `_test`) is the only thing standing between a typo and losing dev data.

## Datetime note
Store and compare using naive UTC datetimes (`utcnow()` from `services/time_services.py`), not timezone-aware ones — these map to Postgres `TIMESTAMP WITHOUT TIME ZONE` columns. The `Event.start_time` field uses naive UTC. On the frontend, append `'Z'` when constructing a `Date` object so the browser interprets it as UTC: `new Date(event.start_time + 'Z')`.

## Authenticated API calls
New API functions in `api/api.js` read the token from `localStorage` via the internal `authHeaders()` helper — do not pass the token as a parameter (that pattern is only used by the legacy `getMe(token)` function). **Public** endpoints (e.g. `getAllEvents()` → `GET /events`, which powers the public `/calendar` page) must NOT send `authHeaders()`.
