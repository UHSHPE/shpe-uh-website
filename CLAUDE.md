## Project Overview
SHPE University of Houston chapter website. React + Vite frontend, FastAPI + PostgreSQL backend.

## Stack
- **Frontend:** React 19, Vite, Tailwind CSS v4, Framer Motion, React Router v7, Axios, qrcode.react (QR rendering for chair-side event check-in)
- **Backend:** FastAPI, SQLModel (ORM), PostgreSQL 17 (via Docker, `postgresql+psycopg://` — psycopg 3 driver), PyJWT, pwdlib (Argon2 hashing), slowapi (rate limiting)
- **Auth:** JWT bearer tokens via `/login`; `/signup` creates an **unverified** account and emails a verification link (no token returned) — the account can't log in until `/verify-email` confirms it. Self-service password reset via `/password-reset/*`

## Running Locally
**Database** (requires Docker):
```bash
docker compose up -d
```
Starts PostgreSQL 17 on `localhost:5433` (see `docker-compose.yml`). Must be running before the backend or its tests will connect.

**Backend** (requires `.venv` activated):
```bash
cd backend
python main.py        # or: uvicorn main:app --reload
```
Runs on http://localhost:8000

**Frontend:**
```bash
cd frontend
npm run dev
```
Runs on http://localhost:5173

## Continuous Integration

GitHub Actions runs on every push and pull request to `main` and `dev`:

- **backend** — runs a `postgres:17` service container (`shpe_test` db, host `127.0.0.1:5433` → container `5432`) with a `pg_isready` healthcheck, sets `TEST_DATABASE_URL` to point at it, installs `backend/requirements-dev.txt` (which pulls in `requirements.txt` via `-r`), and runs `pytest tests/`
- **frontend** — runs `npm ci`, `npm run lint`, and `npm run build`

Both jobs must pass before merging into `main`.

## Deployment (Vercel Pro + Railway + Squarespace DNS)
Target: frontend on **Vercel Pro** (paid tier — the free Hobby tier bans commercial use and the shop sells merch), backend on **Railway** (~$5/mo, persistent volume mounted at `/data`), DNS at **Squarespace**, nightly backups to S3-compatible object storage. `specs/FUTURE_DEPLOYMENT.md` (gitignored) holds the full runbook.

- **`config.py` is the single knob for every writable path.** `DATA_DIR` derives `RESUME_DIR` and `PRODUCT_IMAGE_DIR`. Unset it reproduces the old `backend/`-relative layout, so local dev is unchanged. The **database is not here** — it lives in Postgres via `DATABASE_URL` — but uploads are still on disk, so a deployment without a mounted volume loses every resume and product image on the next deploy. `config.py` deliberately does **no `mkdir` at import** — creation happens in `create_db()`, so importing it never touches the filesystem (tests monkeypatch these paths).
- **The route modules re-export their upload dir as a module attribute** (`RESUME_DIR = config.RESUME_DIR`), NOT `config.RESUME_DIR` at the call site. Five tests monkeypatch `routes.<module>.RESUME_DIR`/`PRODUCT_IMAGE_DIR` to a `tmp_path`; reading through the config module would bypass the patch and silently break all of them.
- **The database is Postgres** (`DATABASE_URL`, `pool_pre_ping=True` so a container restart doesn't kill the next request). `docker-compose.yml` runs it locally on host port **5433**; production uses a managed instance. `SQL_ECHO=1` turns statement logging on for debugging — leave it off in production, since it logs member emails and PSIDs.
- **`--workers 1` is still a correctness requirement, but for only one reason now:** slowapi keeps rate-limit counters in **process memory**, so N workers makes every limit N× looser, non-deterministically. Nothing warns you. Moving off SQLite removed the second reason (one file, single-attach volume). Multiple workers become viable once the limiter is Redis-backed *and* the uploads volume is shared or moved to object storage.
- **A Railway volume attaches to exactly one service**, so a separate cron service cannot read `/data` — backups have to run in-process. It also means deploys are **not zero-downtime** (the old container must release the volume first). Don't deploy during an event.
- `GET /health` is the platform liveness probe and deliberately **does not touch the DB**, so a transient lock can't get a healthy container killed. `GET /health/db` is the manual readiness check.
- `assert_production_config()` also rejects a CORS origin still containing `localhost`. Without that check a forgotten `CORS_ORIGINS` deploys **green** and then fails every browser call with an opaque CORS error that leaves nothing in the server logs.
- **Secrets on disk that must never enter an image:** `backend/.env`, `backend/secrets/*.json`, and the leftover pre-Postgres `database.db` / `database.db.bak-*` files all still exist locally and are gitignored — invisible to a Git-triggered build, but copied verbatim by a local `docker build` / `railway up`. `backend/.dockerignore` is what prevents that. The old `database.db` still contains every seeded admin account sharing `password123`, so it stays excluded until it's deleted.
- Google Sheets credentials support `GOOGLE_SERVICE_ACCOUNT_JSON` (one-line JSON via `jq -c .`) for deployment, falling back to the `CREDENTIALS` file path for local dev. The autouse `disable_event_tracker_sync` fixture clears **both**.

## Key Rules & Lessons Learned

### Never commit secrets
- `backend/.env` and `frontend/.env.local` must stay out of git
- These should already be in `.gitignore` — verify before any commit

### Backend patterns
- Always use `SessionDependencies` (from `services/dependencies.py`) for DB sessions — do not create sessions manually
- Normalize emails with `normalize_email()` from `validators/email.py` before any DB lookup or insert
- New routes go in an APIRouter under `routes/` (included in `main.py`); new DB models go in `models/` and must be imported in `database.py` so SQLModel registers them before `create_db()` runs
- Use `utcnow()` from `services/time_services.py` for "now" — `datetime.utcnow()` is deprecated and raises DeprecationWarning on Python 3.12
- Tests live in `tests/<area>_tests/`; run with `.venv/bin/python -m pytest tests/` from `backend/` — **the Postgres container must be running** (`docker compose up -d` from the repo root) or every test fails to connect. API tests use the `client` fixture from `tests/conftest.py` (dedicated `shpe_test` Postgres database + auth override); `httpx` is required for TestClient
- Passwords are hashed with `get_password_hash()` from `security/hashing.py` — never store plaintext

### Frontend patterns
- All API calls go through the `api` axios instance in `src/api/api.js` — never use fetch or a raw axios import
- Pages live in `src/pages/`, reusable UI in `src/components/`
- Routes are defined in `App.jsx` — update there when adding new pages
- The About page (`pages/about.jsx`) has its **own hardcoded** 2026-2027 E-Board + Chairs roster (names/positions/emails). This is **separate from and not synced with** `seed.py`'s `COMMITTEE_ROSTER` **or with role assignment** — editing one does NOT update the others, and they can drift (the About chairs use committee role-based `@shpeuhchair.org` emails, while seed users use `<first>.<last>@cougarnet.uh.edu`). Promoting someone to a chair role via `/members` updates the Committees page only; About stays stale until hand-edited (see "President role & chapter admin" — this is deliberate, since About is public and `/committees` requires auth). Cards fall back to an initials placeholder when a member has no `img`, and the email line is omitted when `email` is empty.
- Tailwind v4 is used — do NOT use v3 syntax (e.g. `bg-[color]` utilities are fine, but config is in `tailwind.config.cjs`)
- The home page (`pages/home.jsx`) `#insta` grid is wired to a live **Behold** (behold.so) Instagram feed: a `useEffect` fetches `VITE_BEHOLD_FEED_URL` on mount, takes the first 6 `data.posts`, and renders each as an `<a>` (permalink, new tab) wrapping an `<img>`. Image src is `post.sizes?.medium?.mediaUrl` (Behold-hosted thumbnail) with `post.mediaUrl` (Instagram CDN) as fallback. This is an **external public CDN** — it uses `fetch()` directly, NOT the `api.js` axios instance. On fetch error / unset env var, `instaPosts` stays empty and the original shimmer placeholder renders as fallback so the layout never breaks.

### Styling
- The design-system tokens live in `src/styles.css` `:root` — brand colors (`--shpe-navy`, `--shpe-blue`, `--shpe-red`, `--event-*`), gradients (`--gradient-navy`, `--gradient-orange`), radii (`--radius-*`), shadows (`--shadow-card/pop/modal`), and container widths. Reference these tokens (in Tailwind arbitrary values or inline styles) rather than hardcoding hex. Legacy aliases `--blue`/`--navText`/`--muted` are kept for existing pages.
- Work Sans (the brand typeface) is loaded via a Google Fonts `@import` at the top of `styles.css` and set as the `body` font (`--font-body`) — don't re-import it per page.
- Use Tailwind utility classes first; only add custom CSS to `styles.css` when Tailwind can't do it (e.g. the header member-dropdown classes). `App.css` is unused Vite boilerplate — don't add to it.
- Shared button classes: `.primaryBtn` (navy), `.accentBtn` (SHPE red), `.ghostBtn` (outline).
- Framer Motion is available for animations — use it for page transitions and reveals

### What NOT to do
- Do not use `python-jose` — the project uses `pyjwt` (imported as `jwt`)
- Do not add `python-dotenv` to requirements — it is already a transitive dependency; just call `load_dotenv()` at the top of any file that needs env vars
- Do not create new axios instances — reuse the one in `api/api.js`
- Do not use `React.useState` / `React.useEffect` — use named imports: `import { useState, useEffect } from 'react'`
- Do not call setState synchronously inside a `useEffect` body — the lint config (react-hooks/set-state-in-effect) fails the build. For "reset state when a prop/route param changes" or "prefill once async data arrives", use the render-phase adjustment pattern (compare-and-set during render, like `Header.jsx`'s `prevPath` and `shop-checkout.jsx`'s prefill)
- Do not export helpers/constants from a file that also exports a React component — react-refresh lint fails. Put shared helpers in `utils/` and components in their own files (this is why `StatusPill` is its own component and `utils/shop.js` has no JSX)
- The lint config's `no-unused-vars` only ignores identifiers matching `^[A-Z_]`, and usage inside JSX (like `<motion.div>`) doesn't count — so any file importing lowercase `motion` from framer-motion needs `/* eslint-disable no-unused-vars */` at the top (Header.jsx, profile.jsx, members.jsx all do this)
- Do not put digits (or other symbols) in seeded/test user names — `UserCreate`'s name validator allows only letters, hyphens, apostrophes, and spaces, so a first_name like `Test1` crashes `seed.py` mid-run. Put distinguishing digits in the email instead (that's why the unpaid test member is "Test Unpaid" / `test1@cougarnet.uh.edu`)
- Do not query the database by a role's **display value** — SQLModel persists a Python enum by its **name**, while Pydantic serializes it by its **value**, so the same role reads differently at each layer. `Role.president` is stored as `president` and returned by the API as `"President"`; `docker compose exec db psql -U shpe -d shpe -c "SELECT * FROM \"user\" WHERE role='President'"` matches **zero rows and reports no error**, which looks exactly like "that account doesn't exist". Use the enum name in SQL (`WHERE role='president'`, `'comm_director'`, `'academic_chair'`) and the display string only when comparing against API output — that asymmetry is why `utils/shop.js`'s `SHOP_ADMIN_ROLES` holds `"Communication Director"`-style strings while the backend's holds `Role` members. Also note: `user` and `order` are reserved words in Postgres — any raw psql query against those tables needs escaped double quotes (`\"user\"`, `\"order\"`), unquoted `user`/`order` is a syntax error
- Do not add a seeder without an "already seeded" guard — `seed.py` is re-run to top up new data, so an unguarded one duplicates its rows every time. `seed_events` shipped without one and had quietly accumulated 5 copies of all 3 sample events before anyone looked. Guard on the rows that seeder owns (`seed_events` filters `source_row_id IS NULL`, so sheet-synced events can't mask it), and remember the flip side: a guard means editing the seed data in the file does nothing to an existing db until you clear those rows first
- Do not add a new seeded account without setting `email_verified = True` on it after `create_user()` — `/login` 403s unverified accounts, so the account seeds fine and then silently can't log in. This bit the seeded president: the email-verification feature and the president seed were developed on separate branches, so the merge was textually clean and left `seed_president` as the one seeder missing the flag. Any seeder added while a branch is out of date needs the same check
- Do not add a delete/sweep pass to `sync_events` — the duplicate left behind by a rescheduled event is intentional (see "Event tracker sheet sync"); deleting silently kills reminders and resets points
- Do not hard-delete a shop `Product` (and do not unlink its image when retiring) — `DELETE /shop/products/{id}` is a **soft delete**; destroying the row breaks restore and throws away the image a restore needs (see "Merch shop")
- Do not pair `.catch(() => {})` with a success toast in the frontend — the user sees "saved" when nothing saved. Surface `err.response?.data?.detail` via `showToast` like `saveProduct`/`retireProductRow` do
- Do not enforce a cart rule on the page that happens to trigger it — put it in `CartContext.addItem`. There are several entry points (product page, storefront, `MyOrders` re-order) and a per-page check silently misses the next one added. Note `CartProvider` now calls `useAuth()`, so **it must stay nested inside `AuthProvider`** in `main.jsx`; swapping the provider order throws on render
- Do not expect a `<Link to="/page#anchor">` to scroll anywhere — React Router changes `location.hash` but never scrolls. The target page needs its own `useEffect` calling `scrollIntoView` on the hash (see `pages/profile.jsx` for `#orders`)
- Do not put a multi-step wizard's steps in one `<form>` without guarding the submit handler by step — Enter in any text input submits the whole form, POSTing a half-filled payload (see "Signup form"). Guard with `if (step < LAST) { nextStep(); return; }`
- Do not validate a signup field only on the backend. Anything `UserCreate` requires must also be checked in the matching step of `signup.jsx`, or the member fills in five steps and gets a 422 naming a field from step 4 (that's exactly how `country_origin` behaved)
- Do not use a Google **service account** to upload to a personal My Drive folder — Google 403s it (`storageQuotaExceeded`); use the OAuth refresh-token credentials instead (see "Google Drive resume sync")
- Do not call blocking I/O inside an `async def` handler — it runs **on the event loop** and freezes the server for *every* user, not just that request. This already bit twice: `send_email` (blocking `smtplib`) was called straight from `async def signup` and `async def request_password_reset`, and `authenticate_user` (argon2id, 64 MiB / ~100 ms) from `async def login_for_token`. Wrap them in `await asyncio.to_thread(...)` — `auth_routes.py`'s HIBP call is the pattern to copy. Note `smtplib.SMTP()` also defaults to **no timeout**, so one unresponsive mail host hangs the loop forever; `send_email` now passes `SMTP_TIMEOUT`
- Do not key rate limits on `request.client.host` (slowapi's default `get_remote_address`) once the app is behind a proxy — that address is the **proxy's**, identical for every visitor, so all four limits silently collapse into one global bucket (5 signups/hour for the entire chapter). `services/rate_limit.py`'s `client_ip` reads `X-Forwarded-For` and takes the **rightmost** entry: the leftmost is client-supplied and trivially spoofed. Same reason `--forwarded-allow-ips=*` is not a fix — uvicorn's `ProxyHeadersMiddleware` takes the leftmost
- Do not size rate limits for a single user. At a GBM most attendees share **one public IP behind campus NAT**, so a per-IP limit tuned for one person starves the whole room. The limits are env-tunable (`RATE_LIMIT_*`) and default high on purpose; the controls that actually stop abuse are per-**account** (email verification, HIBP check, 10-attempt lockout) and NAT can't defeat those. Tests derive their loop counts from the constants via `limit_count()` rather than hardcoding — don't reintroduce a magic number
- **QR check-in is the extreme case of the above** — its entire premise is a few hundred people scanning within minutes from one room on one network. `/events/attend` originally shipped at `20/minute` per IP, i.e. ~20 check-ins per minute for the whole GBM with everyone else getting a 429 at the door. It now uses `ATTEND_LIMIT`/`CODE_PREVIEW_LIMIT` (600/minute). This is safe because the endpoint's real guards are per-account: it requires a valid JWT, and `EventAttendance` is keyed `(user_id, event_id)`, so a repeat scan returns "already recorded" and awards no points (`record_sign_in` checks for the row and catches the `IntegrityError` from two scans racing). Don't tighten these back toward a per-person number
- Do not hardcode a rate-limit count in a test — import the constant and use `limit_count()`, or retuning a limit breaks unrelated tests (this caught three)
- Do not give product images a deterministic filename. They're served with `Cache-Control: immutable`, so reusing `product_<id>.<ext>` would make every browser and CDN serve the **old photo forever** after a replacement. `upload_product_image` appends `secrets.token_hex(4)`; `productImageUrl` mirrors it with `?v=<image_filename>`
- Do not call `PasswordHash.recommended()` per hash — it builds a fresh argon2id hasher every time. `security/hashing.py` holds one module-level instance

## President role & chapter admin
- **`Role.president` is the site-wide admin** — it was already in the Role enum; what's wired to it: membership in `SHOP_ADMIN_ROLES` (full shop manager), a bypass in `require_chair` + message access (every committee's chair tools), and the `/admin/*` endpoints (`routes/admin_routes.py`).
- **Role assignment is a two-tier privilege, not president-only.** `ROLE_ADMIN_ROLES = {president, vpe, vpi}` (`models/user/user_enums.py`, next to `SHOP_ADMIN_ROLES`) gates all `/admin/*` endpoints via `require_role_admin` in `services/dependencies.py` (mirrors `require_shop_admin`; it replaced the old `require_president`, which no longer exists). The **VP-specific limits are per-request, not in the gate** — `_assert_may_assign` in `admin_routes.py` 403s a non-president who tries to (a) assign a `TOP_TIER_ROLES` role or (b) modify a target who currently holds one. `TOP_TIER_ROLES = {president} | VP_ROLES`, so a VP can neither grant nor strip the presidency *or* either VP seat. Both halves are needed and for the same reason: without (b) a VP could demote the president or their peer; without (a) they could mint an ally into a peer seat, which is the same power one step removed. `GET /admin/roles` filters the whole top tier out of a VP's list so the dropdown can't offer a pick the PATCH would reject — that's convenience; `_assert_may_assign` is the enforcement, keep both.

## Reporting structure (org chart)
- **It grants no permissions. This is the single most important thing about it.** `models/role_report.py` + `services/structure_services.py` record who oversees whom for display; no permission check anywhere consults them. An officer with ten chairs under them has exactly the privileges their `Role` grants — role assignment stays gated by `require_role_admin` + `_assert_may_assign`. `test_supervising_grants_no_permissions` in `tests/admin_tests/test_structure.py` pins this down; if it ever fails, the tree has quietly become an authorization system.
- **Role→role, not person→person.** `RoleReport(role PK, supervisor_role)` — one row per managed role, so "one supervisor per role" holds by construction and a re-parent is an upsert. Keyed this way the tree survives elections and chair handovers untouched, the same reasoning behind `Committee.chair_role` mapping a role (not a user) onto a committee. Co-chairs share a role and therefore share a supervisor.
- **Tier rules** (`structure_services.valid_supervisors`): officers report to a VP; chairs report to a VP or an officer; the president is the root and VPs always report to them, so **neither is stored** — `get_structure` synthesizes the VP→president link. Because every allowed edge points strictly upward a cycle is unreachable, so there is deliberately no cycle check to maintain. Violations are 400.
- The Structure tab renders a **real tree**, not an indented list: `StructurePanel` groups nodes into a `supervisor_role -> children` map and `OrgBranch` recurses from the president. Nesting is therefore **driven by the data, not by tier position** — a chair parked directly under a VP lands in the right place with no special case. Roles with no supervisor can't hang off the tree at all, so they're surfaced in a separate "Not in the chart yet" panel instead of silently vanishing. The elbow connectors are the `.orgTree` rules in `styles.css` (pseudo-elements can't be inline styles — the documented exception); everything else on the panel stays inline like the rest of the page.
- `GET /admin/structure` returns all 23 tree roles (president + 2 VPs + 6 officers + 14 chairs) in `Role` declaration order — which already reads president → VPs → officers → chairs, so the frontend needs no sort. Each node carries its `tier`, `supervisor_role` (**null = unassigned**, surfaced in the UI), and `holders` (empty = vacant). Two queries total.
- **New table, so nothing extra was needed** — `create_all()` builds missing *tables* at startup. Registered in `database.py` next to the other models.
- `seed.py`'s `DEFAULT_REPORTS` is the chapter's **real 2026-2027 org chart** (20 links covering all 6 officers and all 14 chairs): NMR/Treasurer/Regional Rep under VPE, Comms Director/Secretary/DIA under VPI, chairs beneath those. `seed_structure` **skips entirely once any link exists**, so re-running `seed.py` to top up other data never stomps edits made on the Structure tab — to reload from the file, `docker compose exec db psql -U shpe -d shpe -c "DELETE FROM rolereport;"` first, then re-seed.
- The chart has a **"Mini Eboard"** under the New Member Rep that is **not seeded** — there is no such `Role`, and inventing one would mean an enum entry, a committee mapping, and About-page fallout for something that looks like a program rather than a chair seat. Add a `Role` first if it should appear in the tree.

## Event tracker sheet sync
- `services/event_tracker_services.py` pulls the chapter's event-tracker Google Sheet (gspread, **read-only** `spreadsheets.readonly` scope, service-account creds via `CREDENTIALS` + `SHEET_ID`) and reconciles it into the `Event` table. `main.py` runs `sync_events` in a background asyncio loop that fires **daily at 6 AM Central** (`SYNC_HOUR` + `seconds_until_next_sync`, started in `lifespan`). Unconfigured = dev-mode no-op: `fetch_sheet_events()` prints and returns `[]`.
- **Identity is `Event.source_row_id` = `event_key(date, title)` → `"2026-08-05|gbm 1"`** (ISO date + lowercased, whitespace-collapsed name). This is the *join* between a sheet row and a DB row — the auto-increment `Event.id` can't serve that role because the sheet has no column holding it, so without the key every sync would re-insert everything. The column is `index=True, unique=True`; **NULLs stay exempt** (SQL unique indexes treat NULLs as distinct), which is what lets `seed.py` and hand-added events coexist.
- **There is deliberately NO delete/sweep pass** — rows are only created or updated. All of the following are accepted tradeoffs, not bugs:
  - **Rescheduling adds a row instead of moving one.** A new date means a new key, so the old row stays behind and the calendar shows both. Chosen over a sweep because delete+reinsert mints a new `Event.id`, which silently orphans `EventReminder` **and `EventHost`** rows (the join in `send_due_reminders` simply stops matching — no email, no error, and the calendar button resets as if the member never set it) and resets `points_value`, which doesn't exist in the sheet (`event_type` would actually come back correctly, since it's sheet-derived now — the `Event.id` churn is the disqualifying problem regardless). A visible duplicate someone fixes by hand beat a silent failure.
  - **Renames behave the same way** — the name is half the key.
  - **Deleting a sheet row does not remove the event.** The chapter confirmed nobody deletes rows.
  - If a sweep is ever added, it MUST scope to `source_row_id IS NOT NULL`, bail out when the fetch returns zero rows (an unconfigured or failed fetch returns `[]`, which would otherwise wipe the entire calendar), and decide what happens to existing reminders.
- `EXCLUDED_EVENTS` (normalized names — currently `"c&e retreat"`, `"national convention"`, `"thanksgiving break"`) are dropped in `parse_row` before the date is even parsed. **One-way door:** because nothing deletes, an event already synced before its name was added to the set stays in the DB forever.
- Row handling: the header row and the row-2 template row are skipped (`get_all_records()[1:]`), and a per-row `try/except` isolates failures so one unparseable date doesn't kill the batch. Note `parse_row` reads DATE with direct indexing (`row[COLUMNS["date"]]`), so renaming that sheet header would make **every** row raise, get swallowed, and log a cheerful "0 created, 0 updated" while doing nothing.
- Times: `parse_time` returns None for blank / `All Day` / `TBD`, so those events fall back to **local midnight**. `end_time` is built from the same `day` as the start — an event crossing midnight would store an end *before* its start. Confirmed no chapter events run past midnight; revisit if that changes.
- `parse_date` stamps the **current Central year** onto the sheet's MM/DD values. This is correct in normal use because the trackers are **semester-scoped** — the fall sheet runs Aug–Dec and spring is a separate sheet (Jan–May), so every row in one pull shares a calendar year. Do NOT "fix" this by adding a year column; it isn't needed.
- **The one hazard is `SHEET_ID` still pointing at the fall sheet on January 1.** The 6 AM sync then re-reads `09/15` as September of the *new* year, minting a new key for every row and inserting the entire fall semester as ghost events dated a year out — which persist, since nothing deletes. Either swap `SHEET_ID` to the spring sheet before January, or make `parse_date` anchor to the academic year (`now.year` if `now.month >= 8` else `now.year - 1`; months 8–12 take the anchor, 1–7 take anchor + 1), which keeps `09/15` at 2026 even when read in January 2027.
- Duplicate keys inside one pull collapse to one row: the first row is `session.add()`-ed but still pending, and the second row's existing-lookup SELECT triggers SQLAlchemy's autoflush, which writes the first INSERT before the query runs — so the second row finds it and updates in place. Result is `(created, updated) == (1, 1)` and one row holding the *second* row's values, no `IntegrityError`.
- **Credentials live in `backend/secrets/`** (gitignored via `backend/.gitignore`, alongside `.env`), and `CREDENTIALS` is conventionally the relative path `secrets/<file>.json`. `Credentials.from_service_account_file` resolves that against the **process CWD**, so it only works when the backend is started from `backend/` — which is how the project is run and how the tests run. An absolute path is the fix if that ever changes; a wrong CWD surfaces as `FileNotFoundError` swallowed by `event_sync_loop`'s `except`, i.e. a calendar that silently never populates.
- **`event_type` and `EventHost` are populated by every sync**, via `resolve_committee`/`get_event_type` in `services/event_tracker_services.py` (reading the `OWNER(S)` and `COLLAB(S)?` columns). Two lookup tables, both keyed on the **sheet's own spelling** (lowercased, whitespace-collapsed) rather than `Committee.name`, because they differ (`"wellness & athletics"`, `"project"`, `"shpe jr."`, `"eec"`, `"cfc"` vs the DB names in `seed.py`): `COMMITTEE_ROLES` (16 keys → the 14 chair `Role`s) and `EBOARD` (10 sheet abbreviations for E-Board positions — `"vpe"`, `"communications"`, etc, **not** `Role` display values). `EBOARD` is a **dict, not a set** (it was a set until E-Board got `Committee` rows): each specific position maps to its `Role` so `EventHost` rows get written, and the bare `"eboard"` catch-all maps to **`None`**, which is a *real* match — the generic "E-Board" committee has `chair_role=None`. That's why `resolve_committee` returns a **`NO_MATCH` sentinel** instead of `None` for "not recognized at all": once `None` became a legitimate resolution it could no longer double as the miss signal, and `parse_row` filters `host_roles` on `is not NO_MATCH`. Using `None` for both would silently link every blank `OWNER(S)` cell and every outside-org collab (`"NSBE"`) to the generic E-Board committee. **The two dropdowns (OWNER(S) vs COLLAB(S)?) disagree on spelling** for two of the fourteen committees, so `"project"`/`"projects"` and `"shpe jr."`/`"shpe jr"` each get their own `COMMITTEE_ROLES` key mapping to the same `Role` — two divergences in fourteen committees is a high enough rate that it's worth re-checking both option lists by hand if a 15th committee is ever added. `_normalize_owner` strips a trailing `"- <chair name(s)>"` and `"Chair"/"Chairs"` so one function reads both columns: OWNER(S) has both to strip, COLLAB(S)? has neither so both strips are no-ops and a bare value falls straight through. **Logging is deliberately asymmetric**: `resolve_committee` (COLLAB(S)?) stays silent on a miss — an outside org (`"NSBE"`) is the normal case, not an anomaly; `get_event_type` (OWNER(S)) warns on a miss and still files the event under `"eboard"` rather than `None`, so a genuinely unrecognized value (a new dropdown option, a typo) stays reachable by whoever's most likely to notice it, instead of vanishing from every tab with `event_type = None`.
- **`sync_events` reconciles `EventHost` rows** from the parsed `host_roles` list (owner role + collab role, resolved via the same lookup, `None`s dropped in `parse_row`). `host_roles` is popped off the parsed dict as the first statement inside the loop — it isn't an `Event` column, and unlike `Event(**data)` (which silently drops an unrecognized constructor kwarg), `setattr` on an already-built SQLModel instance raises `ValueError` on one, so it must come out before the create branch *and* the update branch. A `Role -> Committee.id` map is built once per sync, not per row, and a newly-created `Event` needs `session.flush()` before its `.id` exists for the host lookup. **Reconciliation deletes stale host rows** (the `existing - wanted` set difference) — a deliberate, narrow exception to this file's no-delete rule above: unlike `Event`, `EventHost` has no dependents, so dropping a row no longer in the sheet is safe, and leaving hosts additive-only would let a chair keep seeing — and minting QR codes for — an event they were dropped from as a collab. The mirror-image `wanted - existing` add-only-what's-missing is what keeps a second sync from raising `IntegrityError` on the composite PK instead of just leaving the row alone. A role with no matching `Committee` row logs a warning and is skipped rather than failing the sync.
- **The QR attendance backend is built** (see "QR attendance & points" below). `EventHost` is what scopes a chair to an event, so the host reconciliation above is load-bearing for permissions, not just display.
- Tests live in `tests/event_tracker_tests/` (`test_event_parsing.py`, `test_event_sync.py`) and use two deliberate seams: `fetch_sheet_events` tests monkeypatch `get_worksheet` with a fake worksheet so the real parse path runs, while `sync_events` tests monkeypatch `fetch_sheet_events` directly so they only exercise DB reconciliation. ## QR attendance & points
- **Members earn points by scanning a QR at an event.** The QR encodes a **URL to our own site** (`/attend/<code>`), so the member's **native phone camera** opens it — there is deliberately **no in-app scanner**, no camera permission, and no QR-decoding dependency. The code in the QR is the same secret either way, so a scanner would add cost and buy nothing.
- **Each event has two codes** (`Event.sign_in_code` / `sign_out_code`, both `index=True, unique=True`), plain random strings from `secrets.token_urlsafe(16)` — a QR is a rendering of a string, nothing binary is stored. Minted lazily by `ensure_event_codes()` the first time a chair views the event (idempotent), **not** at sync time.
- **`resolve_code()` is why there's one endpoint and one page for both QRs.** Both codes live on the same row in different columns, so the scanned string alone doesn't say which it is; it looks up `sign_in_code`, then `sign_out_code`, and returns `(event, "in" | "out")`. Because the action rides on *which code was scanned*, a mislabeled QR is impossible — don't "simplify" this into two endpoints that take the action as a parameter.
- **Points come from the rule alone — `default_points()` — and nothing is stored on `Event`.** Regular event `(2, 2)`, GBM `(3, 2)`. There are deliberately **no per-event overrides**: chairs cannot edit point values. `Event.points_value` is now **computed on read** by `_event_out()` in `event_routes.py` (the raw column stays 0), which is what feeds the `+N pts` badge at `pages/dashboard.jsx:106`.
- **GBM detection is `event_type == "eboard"` AND `"GM" in title`, and the case-sensitivity is load-bearing.** A `.lower()` match would also hit ordinary words containing "gm" (e.g. "Segment"). Both halves are needed: `eboard` alone would promote "Cat's Back Day", and the title alone would promote "SHPE JR 1ST GM" (a committee's GM, `event_type = shpe_jr`). Verified against the live sheet data — the conjunction selects exactly the 5 real GBMs.
- **Codes expire when the event ends — that is the whole replacement for revocation.** There is no regenerate/revoke endpoint and no need for one. `is_expired()` uses `event.end_time or _end_of_local_day(event.start_time)`, and **the Central-day fallback is load-bearing**: many events have no `end_time`, and blank / `All Day` / `TBD` sheet times already fell back to local midnight, so keying expiry on UTC midnight would expire those events *before they started*.
- **A code also doesn't work more than 60 minutes before `start_time`** (`attendance_services.is_not_started`, `NOT_STARTED_GRACE_MINUTES`) — `POST /events/attend` 425s a scan that arrives earlier than that. The grace window (not a hard `now < start_time`) is deliberate and asymmetric with `is_expired`'s end-of-local-day fallback for the same underlying reason: many events' `start_time` is a sheet-sync midnight fallback rather than the real door time, so a hard check would reject nobody there (midnight is early, not late) while rejecting a member who shows up 10 minutes early to a real timed event. The frontend normally never triggers the 425 — `GET /events/code/{code}` (the mobile flow's preview call) reports `state: "not_started"` first and the page renders the "Check-in hasn't opened yet" screen without ever POSTing; the 425 is the backstop against a direct POST.
- **Never double-award — `User.points` is a running total.** A repeat sign-in returns **200 "already signed in"** with `points_awarded: 0` (a double-scan must not look like a failure), not an error. `record_sign_in` guards with a `session.get()` check **and** catches `IntegrityError` for two simultaneous scans racing past it. `EventAttendance`'s composite PK `(user_id, event_id)` is what makes the new-member bonus structurally once-per-event.
- **"Did you bring a new member?" is +2** (`NEW_MEMBER_BONUS`), asked **only on the sign-in scan**, and captures `new_member_name`. Honor-system: the name makes it auditable, not enforced.
- **The "Assist" point values on `pages/membershpe.jsx` (Outreach +4, Professional +3, …) are a SEPARATE process** — they're for *helping run* an event, not attendance. Do not fold them into `default_points()`.
- **Two-layer access control, and both layers are needed.** `require_event_host` (in `dependencies.py`, mirrors `require_shop_admin`) is a coarse role gate — any chair or E-Board member. The per-event scoping lives in `attendance_services.host_scoped_events()` and goes **through `EventHost`**; an unscoped `is_chair` check would hand every chair every event's codes. Same relationship `require_chair` has to committee-specific checks. The president's full-access bypass lives in `host_scoped_events`, not the gate (they already pass it, since `TOP_TIER_ROLES ⊆ EBOARD_ROLES`).
- **E-Board members see every E-Board event**, resolved as `Committee.joinable == False` rather than by re-deriving from `EBOARD_ROLES` (which would miss the generic row, whose `chair_role` is `None`). Officers run GBMs collectively, and keying on the **live** `user.role` means access self-corrects after an election instead of drifting with stale membership rows.
- **`Committee.joinable`** (default True) is False for the 10 E-Board rows `seed.py`'s `EBOARD_COMMITTEES` creates — 9 keyed to a position's `Role` plus one generic `"E-Board"` (`chair_role=None`) for the sheet's bare `"eboard"` value. They exist **only** so `EventHost` has something to point at; they are not committees members can join, and `get_all_committees()` filters them out so `/committees` is unchanged. `_sync_chair_memberships` needed **no change** — it already keys purely off `Committee.chair_role` with no `CHAIR_ROLES` restriction, so assigning someone VPE creates their `is_chair` row automatically.
- **Neither code may ever appear on `EventOut`** — it's public and powers `/calendar`. Codes live on the separate `EventChairOut`. `test_public_events_endpoint_never_exposes_codes` pins this; if it fails, the calendar is leaking sign-in codes to anonymous visitors.

## Merch shop (spec: specs/shop/shop-page.md)
- **Payments — Square Web Payments SDK + Payments API** (`services/square_services.py`). Configured via `SQUARE_ACCESS_TOKEN` + `SQUARE_LOCATION_ID` (+ `SQUARE_ENVIRONMENT`, default sandbox — all read at **call time**) on the backend, `VITE_SQUARE_APP_ID` + `VITE_SQUARE_LOCATION_ID` on the frontend. The checkout page loads `square.js` from Square's CDN (required — it serves the secure card iframe; sandbox vs prod build is picked by the `sandbox-` app-id prefix), renders the card element in the payment step, and `card.tokenize()` swaps card data for a one-time token — card numbers never touch our server (PCI stays minimal). No webhooks: the charge response is synchronous.
- **Charges are itemized in Square** via the Orders API: the route mirrors the validated cart into `line_items` (`{"name": "Product (Size)", "quantity", "unit_price_cents"}`) and `charge_card` creates a Square order from them (`_create_itemized_order`), then passes its id as `order_id` to `payments.create` — the Dashboard shows per-item detail and item names flow into Square's sales reports. Gotchas: the Orders API wants `quantity` as a **string**; the line items must **sum exactly to the charged amount** or Square rejects the payment (guaranteed by construction — both come from the same validated lines); itemization is best-effort — if order creation fails, it logs and charges un-itemized rather than blocking the buyer. These are ad-hoc line items (no Square Catalog sync); if per-item unit counts in Square's Item reports ever need to be exact across renames, the upgrade path is mirroring products into the Square Catalog and passing `catalog_object_id`.
- **Charge order-of-operations in `POST /shop/orders`: validate → charge → persist.** The route calls `shop_services.validate_order_items` (returns `(lines, total_cents)` without persisting), charges that server-side total via `square_services.charge_card`, then passes the same `validated` pair into `create_order` so the stored total always equals the charged amount. A declined/failed charge raises `PaymentError` (buyer-safe message) → 402 with **no order row**; missing token while configured → 400 before any charge. `charge_card` returns a `ChargeResult(payment_id, receipt_url)` NamedTuple (None in dev mode): `Order.square_payment_id` records the payment id (internal — NOT in `OrderOut`), and `receipt_url` goes into the buyer's receipt email. The route is sync, so the blocking Square client already runs in FastAPI's threadpool — if it's ever made `async def`, wrap the charge in `asyncio.to_thread`.
- **Wallets (Apple Pay / Google Pay)** ride the same flow — no backend changes. The payment-step effect builds a `paymentRequest` (display amount only; the backend still charges its own recomputed total) and tries `payments.applePay()` / `payments.googlePay()`; each **throws where unsupported** (Apple Pay: sandbox, non-Safari, unregistered domain — expected, not a bug) and its button just stays hidden. `handlePay(walletMethod)` tokenizes whichever method is passed (the card element when null); a wallet-sheet `Cancel` result is silently ignored. Gotchas: the `#google-pay-button` container must exist in the DOM **before** `attach()` (it renders always, `display:none` until ready); the Apple Pay button is our own `<button className="applePayBtn">` (native `-apple-pay-button` vendor appearance — CSS lives in `styles.css`, Tailwind can't express it); the init effect depends on `[step, subtotalCents]` so a cart change rebuilds the paymentRequest. Going live with Apple Pay needs a one-time domain registration (Square Developer Dashboard → Apple Pay) + hosting Square's verification file at `frontend/public/.well-known/apple-developer-merchantid-domain-association`.
- **Unconfigured = dev mode, end to end** (same pattern as `email_services.py`): `charge_card` prints `[square dev mode] would charge …` and returns None, orders are created with `square_payment_id=None`, and the frontend keeps the demo card block + fake 1.3s delay. **Except when `ENVIRONMENT=production`** — then the dev-mode fallback is a security hole (silent free orders), so `main.py`'s `assert_production_config()` (first line of `lifespan`) refuses to boot with missing Square/SMTP config or a sandbox `SQUARE_ENVIRONMENT`, and `charge_card` raises `RuntimeError` (→ 500, no order row) instead of simulating. - **Dues rules & banner**: dues are **one per member per membership year, enforced server-side** — `shop_services.enforce_dues_rules` (called in `place_order` after validation, before charging) caps dues quantity at 1 per order, rejects guests (the purchase must attach to an account), and 400s a repeat purchase **within the current period**; a **cancelled** dues order doesn't count as paid (`has_paid_dues` matches on the `OrderItem.product_name` snapshot, so it survives product edits/retires). **Yearly reset**: dues reset every **May 30** — `has_paid_dues` only counts non-cancelled dues orders with `created_at >= current_dues_period_start()` (the most recent May 30, this year's if today is on/after it else last year's), so after the reset `has_paid_dues` flips back to False, the banner returns, and the member owes dues again. Change the reset date via `DUES_RESET_MONTH`/`DUES_RESET_DAY`. The cart enforces this client-side in **two** places, both in `CartContext`: `lineCap()` returns 1 for the dues product regardless of the shop-wide item cap, and `addItem()` **refuses dues outright when `user.has_paid_dues`** (toast: "You've already paid your dues this year"). The refusal lives in `addItem` rather than on the pages because there are several ways into the cart — the product page, the storefront, and `MyOrders`' re-order shortcut — and a per-page check misses whichever one is added next (that's exactly how the re-order path shipped able to re-add a paid dues order; the server 400'd it at checkout, so the symptom was a confusing late failure rather than a double charge). `UserOut.has_paid_dues` is **computed in `/me`** (not a DB column) and drives `components/DuesBanner.jsx` — a fixed red banner just below the header (top `var(--header-height)`, z-index 900 < header's 1000) shown to signed-in members who haven't paid, listing the benefits; its CTA and the signup redirect share `utils/dues.js` (`startDuesCheckout`). `shop-checkout` calls `AuthContext.refreshUser()` after a successful order so the banner clears without a reload; the dues product page locks the quantity stepper to 1 and swaps the add-to-cart button for an already-paid note. NOTE: `/me` fails validation for users with zero multi-select rows (UserOut requires ≥1 of each) — tests hitting `/me` must seed those rows (see `test_dues_rules.py::test_me_reports_dues_status`).
- **Frontend**: cart state lives in `context/CartContext.jsx` (localStorage key `shpe_cart`, lines merge by product+size, drawer + 2s toast included); `CartDrawer`/`ShopToast` render once in `App.jsx`. Category filter pills on `/shop` are derived from the `product_type`s present — never hardcode "Stickers". `createShopOrder` sends `authHeaders()` (empty for guests) so member orders link. The Shop Manager panel (`components/ShopManager.jsx` — Overview / Products / Orders / Notifications / Settings tabs) lives on its **own page** `pages/shop-manager.jsx` at route `/shop-manager` (moved off the profile page). ## Signup form (`pages/signup.jsx`)
- **Five steps in ONE `<form>`.** Only the last step's button is `type="submit"`; the rest are `type="button"` calling `nextStep()`. That means pressing **Enter** in any text field on steps 1-4 fires the form's submit handler — which used to POST a half-filled payload and surface the API's 422 as unexplained errors (this is why "country of origin is empty" only appeared at the very end). `handleSubmit` now starts with `if (step < STEPS.length - 1) { nextStep(); return; }`, so Enter behaves as Next. **Keep that guard** if you touch the submit path.
- **`touched` is keyed by STEP, not by field** — `{ 2: { psid: true } }`, and `err(field)` reads `touched[step]?.[field]`. This shape is deliberate. A flat `{ psid: true }` map meant every transition had to remember to clear it, and any path that didn't left a fresh step opening covered in "required" errors before the member typed anything (this shipped, and the flat map made it impossible to pin down which writer was at fault — `onBlur`, browser autofill, and the Next handler are all candidates). Keyed by step there is nothing to reset: a step the member hasn't interacted with simply has no entry. **Don't flatten it back.**
- **`validateStepAt(index)` takes the step explicitly** so the final submit can re-check every earlier step (`firstIncompleteStep()`); on failure it jumps back to the offending step and calls `touchAllOnStep(incomplete)`. `validateStep()` is just `validateStepAt(step)`.
- **`FIELDS_BY_STEP` drives which fields `touchAllOnStep` marks.** Adding a validated field means adding it there too, or its inline error never appears.
- `goToStep()` is the only thing that changes step; it clears `submitError` (which is about the step you were on) and no longer touches `touched`. Don't call `setStep` directly.
- **Client rules mirror the backend on purpose** — `NAME_RE` matches `_SAFE_NAME_RE` in `user_schemas.py`, and the password minimum matches `MIN_PASSWORD_LENGTH`. Diverging means the form accepts something the API then rejects after five steps of typing.
- **Phone is US-only, exactly 10 digits.** `formatPhone` rewrites input to `(555) 555-5555` and hard-caps at 10 digits; `validate_phone` in `user_schemas.py` enforces the count server-side (stripping a leading `1` country code). The regex alone accepts 7-20 characters, so the digit count is the real rule.
- **`country_origin` is required and multi-select** — a `<select>` of `constants/countries.js` plus an Add button, rendering chips. It is validated in step 4 (`Background`) like the other multi-selects. The backend requires ≥1 (`UserCreate`), which is what made it a late 422 before.

## Email verification at signup
- `models/user/email_verification.py` — `EmailVerificationToken(user_id, token_hash, created_at, expires_at, used_at)`, same shape as `PasswordResetToken`. **Reuses** `generate_reset_token()`/`hash_reset_token()` (only the SHA-256 hash is stored). Active while `used_at` is NULL and not expired; TTL is 24h. Registered in `database.py` (imported next to `pw_reset_token`).
- `User.email_verified: bool` (on the **User table model**, defaults False). `authenticate_user` stays pure (`User | None`); the verified check lives in the `/login` route (403 "verify your email"). A new column on an existing table needs the in-place ALTER (`... ADD COLUMN email_verified BOOLEAN DEFAULT 0;`) then backfill existing members to 1 — or just reseed.
- **Signup flow** (`routes/auth_routes.py`): `/signup` creates the user unverified, mints a token, emails `{FRONTEND_URL}/verify-email?token=<raw>` to cougarnet_email, and returns a **generic message (no JWT)**. Rate limited by `RATE_LIMIT_SIGNUP` (default 60/hour). **Squat reclaim:** an existing *unverified* account for the same email is deleted (via `_delete_unverified_user`, which also clears the four multi-select child rows + verification/reset tokens — the DB doesn't cascade-delete those child rows on its own, so they'd otherwise be left as orphans) and re-created; only a *verified* email 409s. Re-submitting signup for an unverified email therefore doubles as "resend link". (Postgres sequences never reuse a deleted row's id — unlike SQLite, a later user can't silently inherit the reclaimed id — but the child-row cleanup is still required regardless, since nothing cascades.)
- **`UserBase.psid` is `unique=True`** (`user_schemas.py`, alongside the existing `cougarnet_email`/`personal_email` uniqueness) — a PSID is UH's PeopleSoft ID, a real-world identifier, so it must map to at most one account. `services/user_services.py`'s `get_user_by_psid()` mirrors `get_user_by_email()`. The signup route runs the **same squat-reclaim logic a second time, keyed on PSID, checked SECOND (after email)** — a duplicate PSID against a verified account 409s ("That PSID is already registered.", distinct wording from the email 409 so the frontend message is unambiguous); against an unverified account it deletes the pending row via `_delete_unverified_user` (same child-row cleanup) and proceeds. **Order is load-bearing**: in the common case (the same person re-submitting signup unchanged) one pending row holds both the email and the PSID, so the email branch deletes it first and the PSID branch is a no-op against an already-gone row — checking PSID first would work too for that case, but the comment in `auth_routes.py` documents email-first as the chosen order. If the two lookups instead resolve to two *different* unverified rows, both get deleted, which is correct (both are dead pending rows). `AdminMemberOut.psid` (the admin member-directory schema) is a separate, non-unique field and was deliberately left untouched.
- **Confirm** (`/verify-email`, `EmailVerifyConfirm{token}`): looks up by hash, rejects unknown/used/expired **and orphaned** (user deleted by a later reclaim) tokens with a generic 400, else stamps `email_verified=True` + `used_at` and returns a login JWT. Idempotency: the frontend verify page guards the single-use POST with a `useRef` so React StrictMode's double-invoke doesn't 400 the second call.
- **Seed** sets `email_verified=True` on all seeded accounts (test users, chairs, comms director, president) — otherwise none could log in after a reseed. `tests/conftest.py`'s `make_user` also defaults `email_verified=True` (fixture users are established members); tests for the flow itself live in `tests/auth_tests/test_email_verification.py`.
- **Frontend:** `pages/verify-email.jsx` at route `/verify-email` (in `App.jsx`); signup shows a "check your email" screen instead of logging in; signin maps 403 to a "verify your email" message. `api.js`: `verifyEmail(token)` (public).

## Password reset & rate limiting
- `models/user/pw_reset_token.py` — `PasswordResetToken(user_id, token_hash, created_at, expires_at, used_at)`. Only the **SHA-256 hash** of the raw token is stored (the raw token is high-entropy `secrets.token_urlsafe(32)`, so SHA-256 — not Argon2 — is correct here). A token is active while `used_at` is NULL and `expires_at` is in the future; TTL is 1 hour. Requesting a new reset retires any prior active tokens for that user.
- `services/pw_reset_services.py` — `generate_reset_token()` / `hash_reset_token()`.
- `routes/pw_reset_routes.py` — `POST /password-reset/request` and `POST /password-reset/confirm`. **Never reveal whether an email exists**: request always returns the same 200 body (even if `send_email` fails), and confirm returns one generic 400 for unknown/used/expired tokens. Reset emails go to **cougarnet_email** (the verified UH address). The link is `{FRONTEND_URL}/reset-password?token=<raw>`.
- Confirm reuses the shared `validate_password_strength()` from `models/user/user_schemas.py` (also used by `UserCreate`) — change password rules there, in one place.
- **Password policy (NIST 800-63B style):** min 10 chars (`MIN_PASSWORD_LENGTH`), max 128 (`MAX_PASSWORD_LENGTH`) in `validate_password_strength` (`models/user/user_schemas.py`) — deliberately NO composition rules (upper/digit/special) and NO expiry; both are counterproductive per NIST. The schema validator is **pure/sync only** (pydantic runs it during request parsing) — don't put network calls in it. The breached-password check lives in the routes instead: `services/hibp_services.py` `is_password_pwned()` queries the Have I Been Pwned range API (k-anonymity — only the first 5 SHA-1 hex chars leave the server; **fail-open**: any error logs and allows). `/signup` and `/password-reset/confirm` call it via `await asyncio.to_thread(hibp_services.is_password_pwned, ...)` — as a **module attribute** so tests can monkeypatch — and reject with **422** (not 400 — the reset page shows "invalid link" for 400) *before* any DB mutation / before marking the reset token used. Tests never hit the network: an autouse `disable_hibp_check` fixture in `tests/conftest.py` stubs it to False. Side effect: `seed.py` calls `create_user()` directly (never the routes), so the seed password `password123` seeds fine. The frontend length checks in `signup.jsx` and `reset-password.jsx` mirror the minimum — keep them in sync.
- **Login lockout (per-account):** 10 consecutive failures (`LOCKOUT_THRESHOLD` in `routes/auth_routes.py`) lock the account for 10 minutes (`LOCKOUT_MINUTES`) → **429 "Too many attempts. Try again later."** raised *before* the Argon2 verify (cheap reject; signin.jsx already maps 429 to a "too many attempts" message). Every failure for an existing email increments `User.failed_login_count` and **commits**; an expired lock is cleared (both fields) before the attempt is evaluated; a successful login resets both fields. Wrong credentials stay a generic 401. The two columns (`failed_login_count`, `locked_until`) live on the `User` table model. Complements (does not replace) slowapi's per-IP limit on `/login` — in lockout tests, call `limiter.reset()` between attempts or the IP limit's 429s shadow the lockout's.
- **JWT invalidation:** `create_access_token` sets `iat`; a successful reset stamps `User.password_changed_at`, and `get_current_user` rejects tokens whose `iat` predates it. PyJWT floors `iat` to whole seconds while `password_changed_at` keeps microseconds, so the comparison is at **whole-second granularity with strict `<`** — a token issued in the same second as the reset stays valid. Tokens without `iat` are rejected once `password_changed_at` is set.
- **Rate limiting (slowapi):** the `Limiter` lives in `services/rate_limit.py` (NOT `main.py` — route modules import it, and importing from `main` would be circular). `main.py` attaches it to `app.state` and registers the 429 handler. The four limits are **named constants in `rate_limit.py`, each overridable by env var** — `LOGIN_LIMIT` (`RATE_LIMIT_LOGIN`, 60/minute), `SIGNUP_LIMIT` (60/hour), `ORDER_LIMIT` (60/minute), `PASSWORD_RESET_LIMIT` (20/hour) — so a limit can be retuned for an event without a code change. Routes reference the constants, never a literal. The key function is `client_ip`, **not** slowapi's `get_remote_address` (see "What NOT to do"). slowapi-decorated endpoints must take a `request: Request` parameter, with the `@limiter.limit(...)` decorator **below** the router decorator.
- **`/login`'s per-IP limit bites manual curl verification.** A script that mints a token per check can burn the budget; login then returns 429, the usual `.get("access_token", "")` yields an empty string, and every following request 401s with "Could not validate credentials" — which reads as wrong credentials, not rate limiting. Mint one token and reuse it across checks, or retry the login until it succeeds.
- slowapi's counters are in-memory and persist across tests in one process — `tests/conftest.py` has an autouse `reset_rate_limiter` fixture calling `limiter.reset()` so counts don't bleed between tests. Auth tests that must exercise real JWT flow use the `unauth_client` fixture (`client` overrides `get_current_user` and bypasses auth).
- The `password_changed_at` column lives on the `User` TABLE model (not `UserBase`), same pattern as `resume_filename`. Adding it required a db rebuild (done); new tables like `passwordresettoken` are created by `create_all()` automatically.
- Frontend: `/forgot-password` (always shows the same "check your email" confirmation) and `/reset-password` (reads `?token=`, new + confirm fields, redirects to `/signin` with `location.state.message` on success — signin renders that message). Sign-in has a "Forgot password?" link and maps 429 to a "too many attempts" error. `api.js`: `requestPasswordReset`, `confirmPasswordReset` — both **public**, no auth headers.

## Profile page & resume uploads
- `pages/profile.jsx` (route `/profile`, in the member dropdown under Committees) shows the signed-in user's info **read-only** (no editing) plus a resume section. It reads everything from `useAuth().user` (the `/me` payload) and tracks resume state locally.
- Resumes are **PDF only** and **private to the owner** (no chair/other-user access). `User.resume_filename` (nullable, on the `User` table model — NOT `UserBase`, so signup is untouched) stores the canonical `First_Last_PSID.pdf` name; `UserOut` exposes it so the frontend knows whether a resume exists. The PDF lives on disk at `backend/uploads/resumes/user_<id>.pdf` (deterministic → re-upload overwrites).
- `routes/resume_routes.py` validates uploads (PDF content-type + `.pdf` ext + `%PDF` magic bytes, ≤2 MB) and serves the file via `FileResponse`. Storage dir is `RESUME_DIR` (a module constant) — tests monkeypatch it to a `tmp_path` to stay hermetic. Every resume is **renamed to `First_Last_PSID.pdf`** (`_canonical_resume_name()` — multi-word names join with underscores, uploaded filename discarded); that canonical name is used for `resume_filename`, the download name, and the Drive copy. The profile page also pre-checks type and the 2 MB cap client-side for instant feedback — keep the two limits in sync.
- **Google Drive sync** (`services/drive_services.py`): when `GDRIVE_RESUME_FOLDER_ID` + credentials are set, uploads mirror the PDF to that Drive folder under the same canonical `First_Last_PSID.pdf` name and deletes remove it. `User.resume_drive_file_id` (table model, internal — NOT in `UserOut`) tracks the Drive file: re-uploads **update in place** (same file id → no orphans; 404 falls back to create), and a failed Drive delete keeps the id so the next upload replaces the orphan. Sync is **best-effort**: failures are logged, never raised — the local file in `uploads/resumes/` stays the source of truth, and without config every Drive call is a console-printing no-op (same dev-mode pattern as `email_services.py`). The googleapiclient is blocking → routes call it via `asyncio.to_thread`. Deps: `google-api-python-client`, `google-auth`, `google-auth-oauthlib` (helper script only). Drive tests monkeypatch the two functions on `routes.resume_routes` (they're imported there by name); an **autouse `disable_drive_sync` fixture in conftest.py clears all `GDRIVE_*` env vars** so tests never hit the real API even when `backend/.env` has live credentials (drive config is read at call time, and `load_dotenv()` leaks .env into the test process).
- **Credentials — OAuth only, deliberately.** The backend uploads *as the folder owner's Google account* via `GDRIVE_OAUTH_CLIENT_ID`/`_SECRET`/`_REFRESH_TOKEN`. There is intentionally **no service-account path**: Google 403s service-account uploads to personal My Drive folders (`storageQuotaExceeded`: "Service Accounts do not have storage quota — use shared drives or OAuth delegation"); SA keys only work with Workspace Shared Drives, which the chapter doesn't have — don't re-add one. Mint the refresh token once with `backend/get_drive_refresh_token.py <client_id> <client_secret> [folder name]` (Desktop-app OAuth client; consent screen must be **In production** or refresh tokens die after 7 days). Setup steps live in the README.
- **OAuth is scoped to `drive.file` — one folder only, by design.** The token can only see files/folders the app itself created, never the rest of the owner's Drive. Consequence: `GDRIVE_RESUME_FOLDER_ID` **must** be the app-created folder id printed by `get_drive_refresh_token.py` (the script creates or reuses a folder, default name "SHPE Resume Book") — pointing it at a hand-made folder 404s. The owner can move/rename the folder in Drive freely (sync is id-based), but renaming means a script re-run would create a fresh folder instead of reusing it. Don't "fix" upload 404s by widening the scope to full `drive` — that's the privacy boundary the owner asked for.
- Frontend: viewing fetches the PDF as a **blob** (`getResumeBlob`, `responseType: "blob"`) and opens it with `URL.createObjectURL` — a bearer token can't ride on an `<iframe>`/`<a href>`. `api.js` functions: `uploadResume` (don't set `Content-Type` — let axios add the multipart boundary), `getResumeBlob`, `deleteResume`.
- **Schema changes are wipe-and-reseed, not hand-written ALTERs — and there is deliberately no Alembic (or other migration tool) set up.** A new/changed column on an existing model (e.g. `resume_filename`, `password_changed_at`) needs the dev database rebuilt: `docker compose down -v` (the `-v` is essential — it drops the named volume; a plain `down` keeps `pgdata` and the stale schema survives) → `docker compose up -d` → `docker compose exec db createdb -U shpe shpe_test` → `cd backend && python seed.py`. This is a **pre-deploy-only** workflow: it's free to wipe now because there's no real member data yet. Once the site is live, real migrations (Alembic or equivalent) need to be introduced before this stops being safe — don't keep reaching for wipe-and-reseed against a production database.
- **Native enum types survive a bare `DELETE FROM`.** SQLModel maps Python enums (`Role`, `Classification`, …) to real Postgres `CREATE TYPE ... AS ENUM` types, not a plain text/check-constraint column. Adding a new `Role` value in code and then only deleting rows (instead of wiping the volume) leaves the old `CREATE TYPE` in place with the old value set — the new value doesn't exist in the db until the type itself is recreated. This is the specific reason the reseed procedure above destroys the whole volume rather than truncating tables.
- **Use `postgresql+psycopg://`, not a bare `postgresql://`.** SQLAlchemy 2.0's default dialect for a schemeless `postgresql://` URL is `psycopg2`, which this project does not install (it uses `psycopg` — psycopg 3). Leaving off the `+psycopg` suffix fails at engine-creation time with a driver-not-found error.
- **`pool_pre_ping=True` (in `database.py`) is required, not decorative.** Restarting the `db` container (or `docker compose down`/`up`) invalidates every connection already in SQLAlchemy's pool; without pre-ping the next request reuses a dead connection and fails instead of transparently reconnecting.
- **In CI, a service container's port mapping is `host:container`, and the container side is always `5432`** regardless of what host port is chosen — Postgres inside the container always listens on 5432. Mapping `5433:5433` (matching the host port on both sides) silently binds nothing on the container's actual listening port, and every test fails to connect. `.github/workflows/ci.yml`'s postgres service maps `5433:5432` for this reason.
- **Tests dropping and recreating the schema is exactly why `tests/conftest.py`'s `_test`-suffix guard on `TEST_DATABASE_URL` matters** — the `engine` fixture calls `drop_all()` before `create_all()`, so a misconfigured `TEST_DATABASE_URL` that accidentally points at the dev `shpe` database would wipe it. The guard (`pytest.exit` unless the db name ends in `_test`) is the only thing standing between a typo and losing dev data.

## Datetime note
Store and compare using naive UTC datetimes (`utcnow()` from `services/time_services.py`), not timezone-aware ones — these map to Postgres `TIMESTAMP WITHOUT TIME ZONE` columns. The `Event.start_time` field uses naive UTC. On the frontend, append `'Z'` when constructing a `Date` object so the browser interprets it as UTC: `new Date(event.start_time + 'Z')`.

## Authenticated API calls
New API functions in `api/api.js` read the token from `localStorage` via the internal `authHeaders()` helper — do not pass the token as a parameter (that pattern is only used by the legacy `getMe(token)` function). **Public** endpoints (e.g. `getAllEvents()` → `GET /events`, which powers the public `/calendar` page) must NOT send `authHeaders()`.
